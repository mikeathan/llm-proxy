# ADR-0049: The audit's assessment reads a bounded window digest that the scan result carries

## Context
The owner read a real audit (vertex, v0.77.0, run 06356dd5) and found the model's assessment light: it was given only this scan's hosts and ports and one check finding, while the program also kept 54 findings, the finding history, alerts, the activity feed and daily counts. It also got three facts wrong (devices up, a severity, and "no finding for SSH" while a stored one existed). A run's order is: the model scans and writes, then `Augment` adds known vulnerabilities, host watch, UDP, web, router and stack findings, compares with the last scan and writes the baseline. The baseline keeps only the latest scan, so there was no record of how a day's scans differed. The owner asked for the assessment to use the data of the day (a week for a weekly audit), generically, with no scenario text in the prompt and no new way for the model to breach anything.

## Decision
1. **One pure reader, `netaudit.DigestOf`**, builds a bounded typed digest for `[now - window, now]` from records the program already keeps (the scan log, the finding history, the latest saved scan, the alert log, the daily series, the inventory). It starts no scan and sends no packet. Only the scan log is new: one row per saved audit (counts and finding keys; 14 days, 200 rows), written by the report step after the baseline, never by a model.
2. **The scan result carries it.** `network_scan` appends the digest in its own untrusted-data fence for an audit run only (the run has scan settings); an ordinary chat gets the scan alone. It is attached to the result, not offered as a second tool: a local model told to call the scan once may never call another. The model gets **no new trigger**; route trace (I.14), the router read (I.15), the deep check and the capture stay with the operator or the audit's own code.
3. **Aggregated in code, bounded by bytes.** Exact counts, the latest 12 scan rows, 25 open problems worst first, 15 per change list, newest first, and a 9,000-byte ceiling (about 3k tokens on a dense result) for the rendering (the longest list is halved until it fits, and each cut is stated). A record that cannot be read is named in the digest, so it is never read as a quiet network.
4. **What the digest leaves out, by owner decision (2026-11-12):** findings the operator accepted, and known-vulnerability findings (the report adds those after the assessment, by design). Activity is counts by kind; a device's name, address or hardware address and an alert's text are never in it.
5. **The window is a structured setting** (`ScanSettings.Window`: `day` or `week`, a template header `**Window:**`, a form field), capped in code. The weekly audit is a second template over the same profile.
6. **The count in the tool's header is typed** (devices that answered, of addresses looked at), so the model does not count a list. The prompt describes the data and asks for reasoning across the window, and keeps the facts the code writes (counts, severities, the comparison with the last scan) out of the model's hands.

## Consequences
- The model sees the previous scans' history, not this run's add-ons (they are computed after it writes); the latest saved scan holds the earlier add-ons' findings.
- A scan log row exists only from the first audit after this version; a window with no rows says so.
- The weekly audit's own scan rows are only its own (one a week); the finding history, alerts and inventory are workspace-wide. Reading the daily audit's rows for a weekly one is left open.
- Loosens "the model sees only this scan" for audit runs. The model stays local-only, device text stays inside the fence, and the operator's notes and the router key are never in it.
- 2026-11-12 (v0.78.1, from the first vertex run of v0.78.0): **the digest is reconciled with the scan it travels with, and accepting a check hides its port.** The records end at the scan before this one, so a digest that said "gone" for a port the new scan showed open made the model state it as fact (it cannot diff two lists). `DigestOf` now takes the scan being made (`CurrentScan`, built from the full result): an open TCP port the records call gone is moved to "returned", one they call new or open all window but the scan shows closed is moved to "gone" (dated as of this scan), an open finding whose port is closed now is marked `not_in_this_scan`; UDP, whole-device findings and devices the scan did not finish are left as recorded. The digest names when its records end (`records_end_at`), and an empty scan log beside a saved scan says so instead of "no scan was recorded". `HideAccepted` hid only the bare open-port finding, and the findings are rebuilt from the hosts, so an accepted `telnet_open` came straight back: an accepted check finding now takes its port out of the hosts (a known-vulnerability acceptance does not: it is about those CVEs), and the digest hides every finding on that port. Down addresses are no longer listed in the scan result (a /24 listed 254 `{"up":false}` rows); the header keeps the count.
- 2026-11-12 (v0.78.2, from reading vertex's recordings): **the scan result is sized to the agent's tool-result cap.** The recordings of the vertex audits (v0.77.0 and v0.78.0/1) all show the `network_scan` result cut by the agent: `[SYSTEM TRUNCATED 17809 CHARACTERS]`, a cap of about 10.2K encoded characters on a result of about 27K (indented JSON, filtered ports, an `open_port` finding for every port, the digest). The model read 5 of 15 devices and the end of the findings, so it never saw most hosts, and the digest (budget 9,000, nearly the whole cap) was crowded by the scan. The tool now reads its cap from the call context (`models.ResultCapFrom`), gives the model a compact view (answering devices, open ports only, no open-port findings, guessed service names marked "(guess)", a guessed product left out), cuts whole devices if it still does not fit and says so in the header, and hands the digest what is left (`RenderDigest(d, budget)` measures the encoded text). The digest no longer says "scheduled" or "pressed": the scan log records only that an automation ran the scan.
- 2026-11-12 (v0.79.0, from the v0.78.3 run `adb7df0e` read against its recording): **facts move from the model to code, and a guessed name is not shown to the model at all.** The model kept ignoring wording limits (280 words and about 15 items against 250 and 8) and stated guessed names as fact ("AFS fileserver" for a port labelled "afs3-fileserver (guess)"), so (1) the **exposed services worth reviewing** are now a section of the Observed report written by code (`ExposedServices`, confirmed service names only, one kind each: remote administration, file sharing, database; listed on every run, bounded, escaped) and the model is told not to list them, whatever the task text says (a workspace's task file is an older copy of the template and still asks for them, so the override lives in the profile); (2) a guessed service or product name is **left out** of everything the model reads (hosts, check findings, digest), not marked, through one helper, `ConfirmedText`; (3) one rule for what an acceptance hides, `CoveredPorts`, used by the model's scan view, the digest and the new list; (4) the digest's `serious` count is gone (it counted findings the digest hides). The model's part is now the cross-window reading, at most five items. Rejected: cutting the model's text in code (cuts mid-sentence), and a second service list by port number (`sensitiveForwards` answers a different question).
- 2026-11-12 (v0.80.0, from the v0.79.0 run `9362b046` and its recording): **every fact in the report is written by code, and the model has one narrow job.** The v0.79.0 profile told the model that the Observed section carries "every check's problem with its severity". That is true of a first scan only: a repeat scan lists what is new, resolved or changed, so a high finding open for a day was in no part of the report, and the model, believing it was, left it out too (its 5 items were port movement). Fixed in code, not in wording: the Observed section of a repeat scan now has **Still open** (every check finding not accepted and not already under New checks, through the same `writeChecks` as a first scan, fixes included) and **Last day / Last week before this scan** (the same `WindowDigest` the model reads, built by `DigestSource.Build` through the reporter's `WithWindow`: scans, devices-up and open-port ranges, ports that went away or came back, activity, and what could not be read). The model is asked for at most three items on what to look at first, each naming a finding or change from its input, and told that all of the above is written for it; the task file is a thin pointer to the profile, because a workspace copy of it is never refreshed and had contradicted the profile (it still told the model not to say what changed while the digest carries the window). **Rule for later changes:** a prompt that describes the report must match what `RenderObserved` writes on a repeat scan, not only on a first scan; a fact the report must hold is written by code, never left to the model.
- 2026-11-12 (v0.81.0): **the report says what the background modules did, and reads as a reference rather than a wall.** (1) `stacksdk.ModuleStatus` gets an additive, typed `Recent Tally` (`done`, `flagged`, `unclear`: counts over the last 24 hours, `omitzero`, no free text; the port types are plain data, so a struct and not a pointer). The Network stack fills it from the comparisons its DNS check already logs; the core words it from its own table (`ModuleTally.Line`) and puts it into the window digest, so the report ("Router DNS check, last 24 h: 24 checks, 0 differed, 0 could not be compared.") and the model read one source. It is a 24-hour tally whatever the audit's window, and says so; nothing from a resolver can leave through it, and the core did not import the stack's package or parse its route. (2) The viewer cuts a saved audit report at its code-written headings (`utils/netaudit/auditReport.ts`): the assessment first, what is new and still open in view, and the reference parts (resolved, exposed services, the window, the suggested fixes, the notes) folded to a line that says what is inside; "Ways in that matter" is now a heading so it can be cut; a text without the headings is plain markdown as before. (3) The saved reports are folded to one line with the opened report above them. (4) The running tab is filled with the theme's brand colour, a contrast-proven pair in every preset.
