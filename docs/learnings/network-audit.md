## Root causes and fixes that held

- **Tried:** Letting the model choose scan targets → **an auditor run guessed `192.168.1.0/24`**. **Lesson:** `network_scan` with no targets scans every allowed range. Evidence: [network-audit.md](../PLANS/ARCHIVE/cross-cutting/network-audit.md).
- **Tried:** Trusting nmap's port-table service names → **8081 was read as "blackice-icecap" and described as an IDS**. **Lesson:** mark table names as guesses. Evidence: [network-audit.md](../PLANS/ARCHIVE/cross-cutting/network-audit.md).
- **Tried:** Reading interfaces via netlink under a systemd unit → **no netlink socket on the deployment**. **Lesson:** fall back to the default route's address on a /24. Evidence: [network-audit.md](../PLANS/ARCHIVE/cross-cutting/network-audit.md).
- **Tried:** Running nmap in CI → **decided against (D13)**. **Lesson:** verify nmap under Landlock by hand on Ubuntu; keep CI small. Evidence: [network-audit.md](../PLANS/ARCHIVE/cross-cutting/network-audit.md).
- **Tried:** A one-device rescan through the ordinary audit run → **its baseline write replaced `Unscanned` and `DevicesUp` with the single host's, while findings were already merged per device**. **Lesson:** a run that covers some devices must carry over the rest (`carryOver` in `runreporter.go`). A rescan queued behind the same audit is absorbed by the lane's key dedupe and runs as the full audit. Evidence: [network-audit.md](../PLANS/ARCHIVE/cross-cutting/network-audit.md) §13.A.
- **Tried:** The plan's manual check for nmap under Landlock, `go test -run TestChecks_RealNmap` → **that test runs nmap with plain `exec`, so Landlock is never involved**. **Lesson:** the Landlock check must go through the running app's `progexec` path (one audit on Ubuntu). Evidence: `backend/internal/core/netaudit/nmap/checks_nmap_test.go`, [network-audit.md](../PLANS/ARCHIVE/cross-cutting/network-audit.md) §13.D.
- **Tried:** Reviewing the check scripts for the Constitution text (2026-10-27) → **all nine (of the first list) are in nmap's `safe` category (nmap 7.99), but `ftp-anon` does attempt the anonymous FTP login**. **Lesson:** "safe" is not "sends nothing credential-like"; the guarded-programs text allows exactly that one exchange. Evidence: [network-audit.md](../PLANS/ARCHIVE/cross-cutting/network-audit.md) §13.D.
- **Tried:** Estimating how much of a home network known-vulnerability matching can cover → **6,814 of nmap 7.99's 11,970 service `match` rules (57%; rules, not devices) carry a CPE; application CPEs nearly always have a version slot (1,687 of 1,689), operating-system ones about 195 of 2,525 and hardware about 20 of 1,223; the parser reads none yet**. In NVD's 2026 file only 35,448 of 80,783 CVEs (44%) have configuration data. **Lesson:** coverage is capped twice, by nmap's identification and by NVD's analysis backlog, and firmware flaws are mostly out of reach without `-O`; the UI must show what was looked at. Commands: `grep -c '^match .*cpe:/'` on `nmap-service-probes`; the yearly feed at `https://nvd.nist.gov/feeds/json/cve/2.0/nvdcve-2.0-2026.json.gz`. Evidence: [network-audit.md](../PLANS/ARCHIVE/cross-cutting/network-audit.md) §13.G.
- **Tried:** Reading NVD's pages with the fetch tool → **they need JavaScript; nothing readable came back**; plain `curl` of the API and the yearly files worked. **Lesson:** use `curl` for NVD; its terms and rate limits are still unverified. A search snippet saying the feeds were retired referred to the old 1.x files; the 2.0 yearly files exist.
- **Tried:** One real service scan (2026-10-27, one Ubuntu host on the LAN, the app's flags, `-oX`) to see whether nmap prints CPEs → **yes, in `<service><cpe>`: OpenSSH gave `cpe:/a:openbsd:openssh:9.6p1` (distribution suffix dropped), the kernel gave a versionless `o:` CPE, and the app's own Go API was identified as `go-ipfs` with no version**. **Lesson:** a CPE without a version must never match, and a banner with a distribution build needs lower confidence. Evidence: [network-audit.md](../PLANS/ARCHIVE/cross-cutting/network-audit.md) §13.G Phase 0.
- **Tried:** Reading NVD's rate limits and terms (2026-10-27) → **nvd.nist.gov pages return 403 to plain `curl` and need JavaScript for the fetch tool; search gave only a legal disclaimer and the CPE dictionary's no-copyright statement**. **Lesson:** do not work around the block; read the developer pages in a browser before building any app-side fetch. v1 uses the yearly files and needs no limits. Evidence: [network-audit.md](../PLANS/ARCHIVE/cross-cutting/network-audit.md) §13.G.
- **Tried:** A service scan of the whole home /24 (2026-10-27, owner approved, the app's flags; 6 devices up) → **16 open services, only 3 with a versioned CPE (19%), all application CPEs on Linux servers; router, media and phone-class devices gave none**. **Lesson:** known-vulnerability matching will cover servers, not embedded devices, on a home network; show "looked at N of M services" and do not present silence as safety. Evidence: [network-audit.md](../PLANS/ARCHIVE/cross-cutting/network-audit.md) §13.G Phase 0.
- **Tried:** Importing NVD's real 2026 file into the index (2026-10-27) → **493 MB read as a stream in 2.5 s, 57 MB heap, 33,993 CVEs and 177,604 product ranges; 44,242 CVEs have no configuration data; 1,093 are rejected**. **Lesson:** streaming is enough, a year is about 9 MB compact, and "vulnerable app AND running on platform" rules (about 12% of CVEs) must be indexed from the app part or coverage drops. `NetworkTools.FetchURL` cannot carry the files (text cut near 1 MiB); a download must use `HTTPClient()`. Evidence: [network-audit.md](../PLANS/ARCHIVE/cross-cutting/network-audit.md) §13.G.
- **Built:** Version comparator for `vulnmatch` (2026-10-28) → **numbers compare as numbers; a single letter after a number (`9.6p1`, `1.0.2k`) sorts after the plain release; `rc`/`beta`/`alpha`/`pre`/`dev` sort before it; anything else (unknown word, letter against a number) is "cannot compare" and never matches.** Chosen because a wrong order would turn into a false alarm or a missed flaw, while "could not compare" is counted and shown. Evidence: `core/vulndata/vulnmatch/version_test.go`.
- **Built:** `known_vulns` findings (2026-10-28) → **added in `RunReporter`, not in the scan tool, so the auditor model never sees them; they join `result.Findings` before the diff so the baseline, accept and "changed" work unchanged.** An accepted finding stores the CVE set (`ScanAck.AcceptedCVEs`/`AcceptedExploited`) and comes back only when a CVE not in it appears or one becomes exploited; a smaller set stays accepted. Adding slices made `ScanAck` and `ScanFinding` non-comparable, which broke one `!=` in `persistence/acks_test.go` (now `reflect.DeepEqual`). Evidence: `core/netaudit/knownvulns_test.go`.
- **Built:** Vulnerability-data download (2026-10-28) → **`vulnfeed.Manager` derives its state from what the index holds, so "stopped after 3 of 6" survives a restart without a second state file; resume = fetch the files not held.** The readiness answer gets a separate `notices` list because `Readiness.Preflight` refuses a scheduled audit on ANY item `Check` returns (non-blocking ones included): putting `vuln_data_missing` in `Check` would have stopped every nightly audit until the data was downloaded. `FetchURL`'s guard checks moved into `NetworkTools.Open` (tools on, internet allowed, blocked domains, address vetting) so a streaming download does not re-implement them. Both real URLs answer 200 with no redirect (HEAD, 2026-10-28); a redirect to another host is refused. A `VulnSource` with a `[]int` made the struct non-comparable, which broke one `!=` in `persistence/vulnindex_test.go`. Evidence: `core/vulndata/vulnfeed/feed_test.go`.
- **Built:** Vulnerability-data UI (2026-10-28) → **one shared status in `useVulnData`, polled once a second only while a download runs; the readiness banner builds its progress line from that status instead of the notice text, which is stale between readiness reads.** The banner asks for the status only when the `vuln_data_missing` notice is present, so other pages make no extra request. Module-level shared state leaks between component tests: reset `status`, `error` and `readiness` in `beforeEach`. Settings sections stay mounted, so `NetworkScanSettings` (and its card) loads on every Settings tab: a Playwright spec that mocks the admin API must return `[]`, not `{}`, for the list endpoints (`/profiles` and the rest) or the page throws `props.profiles.filter is not a function`; `e2e/telegram-help.visual.spec.ts` failed that way on 2026-10-28. Every spec now mocks through `e2e/support/adminApi.ts` (`mockAdminApi`), which answers the list endpoints with `[]`, so a new one cannot repeat it. Screenshots "for looking at" are written only with `SCREENSHOTS=1` (`lookAt`); the suite went from 48 s to 17 s. The server's zero date (`0001-01-01`) means "never imported". Dates in tests must be built with the same `toLocaleDateString` as the code, or the test only holds in one locale. Evidence: `e2e/netaudit-vulndata.visual.spec.ts`, `__TESTS__/components/netaudit/netaudit.component.test.ts`.
- **Built:** "Start again" and the out-of-date notice (2026-10-28) → **`Manager.Start(restart bool)` and `?restart=1`; `vuln_data_old` is a notice (never a requirement) computed from `Status.Age`, the older of the two sources, so one stale source is not hidden by the other.** The banner acts on old data in place ("Update now") but sends a missing or half-finished download to the card, where size and progress show. `Settings.component.test.ts` mounted the real network-scan section and fired about 2,000 real requests at a dead port per run; stubbing `NetworkScanSettings` there (as the file's own comment says to do for sections with their own data layer) cut that file from 6.2 s to 3.5 s. The rest of the noise came from `AgentsSettings`, which asks for `/profiles` and `/profile-schema` on every mount (135 requests a run); it is stubbed too (it has its own test), and the full suite now prints no `ECONNREFUSED`. Found by wrapping `net.Socket.prototype.connect` in a temporary copy of the test and printing the request path: a stack trace shows only happy-dom internals. Evidence: `e2e/netaudit-vulndata.visual.spec.ts`, `vulnfeed/feed_test.go`.
- **Checked:** whether the app can run a command on another host, for the assisted-fixes design (2026-10-28) → **no: there is no SSH client or remote-execution tool (nothing in `go.mod`, no `ssh` program started anywhere); the `terminal` tool runs on the app's own machine inside the workspace jail and the OS sandbox, and connectors only send messages.** **Lesson:** the owner's target "hosts configured for terminal or connector access" matches no host today, so a fix that changes another machine (Level 2 in §13.H) needs a new access kind, a Constitution amendment and admin-API authentication first; Level 1 (guided fixes with a record) needs none of that. Evidence: [network-audit.md](../PLANS/ARCHIVE/cross-cutting/network-audit.md) §13.H.
- **Tried:** A playbook paragraph telling the auditor model that the system adds known-vulnerability findings → **the reporter adds them after the scan tool, so the model never sees them, and a model told they exist but shown none may write "none were found".** **Lesson:** anything a playbook says about findings the model cannot see must tell it to stay silent about them. The plan's §13.G "Model-facing" paragraph said the opposite and was corrected. Evidence: `backend/data/templates/network_audit.md`, `core/netaudit/knownvulns.go`.
- **Fixed:** the owner pressed Update on fresh data and saw "Downloading file 7 of 6" and a full download each time (2026-10-28) → **two bugs: the status counted files held (6) and added one while a refresh re-fetched all six, and Update was offered, and honoured by the server, when nothing was old.** **Lesson:** a progress count must come from the job, not from the state it is changing; and a costly action (100+ MB) needs a guard on the server as well as a hidden button, so a double click or a second tab cannot repeat it. Update now exists only for data older than 60 days; `Start(restart)` is the one way to force a refetch. Evidence: `vulnfeed/feed_test.go` (`...FreshStartDoesNothing`, `...CountsFromZero...`).
- **Tried:** The first real audit with known-vulnerability matching (2026-10-28, owner's LAN) → **it worked, but the Advanced row showed only the same one line as Simple: no version, no full list, so a match could not be judged (and a second run of the same port gave 26 flaws, then 28 with CVE-2024-6387, with nothing on screen to explain the difference).** I checked the counts by reading the local index with a short script (28 for OpenSSH 9.6p1; ordering exploited, then score, matched the finding). **Lesson:** a finding built from a matching rule must show its input (the software and version compared) and its full result, or the operator cannot tell a wrong match from a right one; verify against the index file (`vulnindex.json` in the config root) rather than guessing. Evidence: `FindingsAdvanced.vue`, `utils/netaudit/flaws.ts`, `e2e/netaudit-report.visual.spec.ts`.
- **Tried:** Reading the first real findings with the new detail view (2026-10-28) → **two matching bugs.** (1) **A major-only version was treated as x.0:** nmap reports Samba as `smbd 4`, and `4` compared as `4.0.0` matched every flaw whose range starts there, giving 21 "high" findings on two ports. A version of one number is a whole family (4.0 to 4.x): a range now matches only if the whole family lies inside it, is ruled out if the family lies wholly outside, and is otherwise counted as "could not be compared" (`vulnmatch.familyInRange`). On the owner's real index `smbd 4` went from 21 matches to 0 and 37 uncomparable. (2) **The importer dropped NVD's "update" field:** NVD writes OpenSSH 9.9p1 as version `9.9` with update `p1`, so `p1` and `p2` were both indexed as a plain `9.9` that a banner's `9.9p1` never equals (CVE-2025-26465 listed `9.9` twice and was missed for 9.9p1). The update is now part of the exact version (`vulnindex.updateOf`). **Lesson:** an index built before this fix keeps the old entries; the card's Advanced "Start again" refetches everything, because a plain Update does nothing on fresh data. "No score" in the new flaw list was a baseline saved by the build before scores existed: the list fills in on the next run. Also found: the audit had scanned two Ubuntu hosts (OpenSSH 9.6p1 and 9.9p1), which explained why one port showed 28 flaws and another 26. Evidence: `vulnmatch/match_test.go` (`...AMajorVersion...`), `vulnindex/import_test.go` (`...TheUpdateField...`).
- **Fixed:** After the major-version fix the two Samba findings vanished and the report still counted those ports as "compared" (2026-10-28) → **a port whose only version is a bare major number must not count as compared.** `vulnmatch.Result.Precise` is true when some CPE's version can be placed in a release; the coverage line now reads "compared N of M open services… K reported only a major version (for example just “4”), which is too coarse to compare, so they are not covered." **Lesson:** every reason a service is left out of a check has to show in the coverage line, or silence reads as safe. Evidence: `knownvulns_test.go` (`...AMajorOnlyVersion...`), `vulnmatch/match_test.go` (`...Precise...`).
- **Built:** Assisted fixes Level 1 (2026-10-28) → **guides are fixed text keyed by check, a fix record is a note that never hides or changes anything, and "fixed" is only ever claimed by a scan.** Traps: (1) `Collector.Merged` rebuilds findings from the hosts (`FindingsOf`), so a reporter test that passes ready-made check findings silently turns them into open ports; build hosts with script output instead (`smbHost` in `runreporter_test.go`). (2) A record is retired from `delta.Resolved`, which only covers devices the run scanned to the end, so a device that timed out or was not in a one-device rescan keeps its record. (3) A scan already running when the operator marks a finding is stamped with its end time and can read as "still showing". (4) `GetFindings` grew past the complexity limit when the guide and the records were added; a `findingViewer` now builds the views. Evidence: `fixes_test.go`, `runreporter_test.go` (`...MarkedFixed...`), `netaudit_fix_handlers_test.go`, `e2e/netaudit-report.visual.spec.ts`.
- **Built:** Delete the vulnerability data (2026-10-28) → **a button in the card, `DELETE /vulndata`, and a factory-reset cleanup.** Factory reset replaces `settings.yml`, the registry, secrets and the master key and deliberately keeps `meta/` and the database, so a file kept beside them (`vulnindex.json`) survived it until a cleanup was registered (`AppContext.AfterFactoryReset`); wipeout always removed it, being a delete of the whole root. Clear stops a running download first and waits for it, or the job would write the index back after the delete. Also found while reading the shutdown path: the manager had been built with a bare `context.Background()`, which II.2 forbids; the root context only exists after `BuildAppServices`, so the manager is built without one and attached in `app.New`. Evidence: `vulnfeed/feed_test.go` (`TestClear_*`, `TestStart_BeforeTheApplicationIsAttached...`), `app_context_test.go` (`TestFactoryReset_RunsTheRegisteredCleanups...`).

- **Found, not fixed:** Two false "high" findings on a Samba host (2026-10-28) → **vertex (nmap 7.94SVN) printed `Samba smbd 4.6.2` (`cpe:/a:samba:samba:4.6.2`) for a device whose `smbd --version` is `4.21.4-Ubuntu-4.21.4+dfsg-1ubuntu3.5`; 26 flaws matched on ports 139 and 445, and with no distribution marker in the text the severity stayed high.** The same device scanned with nmap 7.99 and the app's flags gave `Samba smbd 4`, `method="probed" conf="10"`, the same method and confidence as OpenSSH: the 7.99 rule is a fixed `v/4/` at `nmap-service-probes:14117`. Why 7.94 prints 4.6.2 was not confirmed (its probe file could not be fetched; check `grep -n "4\.6\.2" /usr/share/nmap/nmap-service-probes` on vertex). **Lesson:** nmap's XML does not say whether a version was read from the service or fixed by a rule, and `conf` is 10 for both, so there is no generic test for "guessed". A Samba-only skip was written and dropped on purpose (owner: no product-specific fixes). The honest handling today is the finding's own wording ("may be affected") plus accepting it with a note. Evidence: scan of one device, 2026-10-28.
- **Tried:** Proposing `ssl-enum-ciphers` and `ssh-auth-methods` as the safest next checks, from memory (2026-10-28) → **on nmap 7.99 the first is `discovery, intrusive` and the second `auth, intrusive` (it tries a random user name); `dns-recursion` and `upnp-info` match UDP only, so `-sT --unprivileged` never runs them.** **Lesson:** read `categories` and `portrule` in the installed `scripts/*.nse` before naming a script; the Constitution list (II.3 item 5) allows no intrusive script. Evidence: [network-audit.md](../PLANS/ARCHIVE/cross-cutting/network-audit.md) §13.B.2.
- **Tried:** Adding extra ports to a thorough scan with `--top-ports 300 -p 2375,…` (2026-10-28) → **nmap ignores `--top-ports` when `-p` is given and scans only the `-p` list.** **Lesson:** a thorough scan names its ports itself (`netaudit.ThoroughPorts`); a check whose port is in neither list never fires, so check the default lists whenever a port rule or script is added. Evidence: `backend/internal/core/netaudit/ports.go`.
- **Tried:** The first real audit's report (2026-10-28, 12 devices, 37 open ports) → **a first scan marked every port "new" (37 cards), 20 of them "(guess) · version unknown"; the same fix paragraph was printed five times; the model's assessment called a `tcpwrapped` port RDP "High", repeated the Samba false positive above and said OpenSSH 9.9p1 had "no vulnerability identified" beside a 28-flaw finding.** **Lesson:** a baseline is not a change; group a problem by kind and write its fix once; tell the model not to re-rank or add severities to what the code established (`security-auditor.md`), because the profile text applies to existing audits while the playbook copy in a workspace does not refresh.
- 2026-10-28: per-device expectations (plan §13.I) are judged from the scan's own findings, so they need no new probe and no Constitution change; a device that is down or unfinished (`Unscanned`) must be skipped, because its ports are unknown, not none. The plan already had a §13.H (assisted fixes): check section numbers before adding one.

- 2026-10-30 (deep check, real-device test): `ssl-enum-ciphers` prints nothing on a port nmap has not identified as TLS, so a deep scan needs `-sV` (as the checks mode has); a device that closes the connection at once (RDP, `tcpwrapped`) or speaks plain HTTP gives it nothing, and the report must say no TLS service answered, not "fine". It opened 58 connections for one port in 28 s; `ssh-auth-methods` opened 2 in 0.6 s with a random five-letter user name. In zsh an unquoted variable is not split into arguments: pass nmap's flags as an array when scripting a manual test.
- 2026-10-30 (deep check, build): `FindingsOf` makes an open-port finding for every port, so a deep result must go through `DeepFindingsOf` (deep checks only), and the stored result must keep which ports a TLS or SSH service answered on, or "nothing found" cannot be told from "nothing to check". A carried finding is not re-checked by the next audit, so its fix state follows the deep check's own time. BSD `sed` has no `\b` and zsh does not split an unquoted variable; use perl and arrays.

- 2026-10-29 (Landlock hand check on vertex, `192.168.50.60`, kernel `7.0.0-38-generic`, nmap `7.94SVN`; the Ubuntu release was not captured): the confinement reads `landlock` (file and network, `GET /admin/api/host`) and `allow_unconfined` is false, so the nightly audit (254 addresses, thorough, checks on, 2026-10-29 02:00, 3m15s) ran confined and still read nmap's data files: it named `Samba smbd 4.6.2` and `OpenSSH 9.6p1`. No "Operation not permitted" or "failed to confine" in the app log. **Pass for confinement.** One "Rescan this host" of `192.168.50.10` (16:36 to 16:37, 71 s, nmap, 1 device up, 8 findings: open ports and `known_vulns`) ran with two `tcpdump` captures on vertex (TCP SYN to anything but the target and not port 22; UDP 53, 5353, 1900). **Pass for "no check script contacts another host" over TCP and DNS on that device:** the only outbound SYN to another host was `192.168.50.60 -> 91.189.91.57:80` at 16:36:17, preceded in the DNS capture by a lookup of `connectivity-check.ubuntu.com` at the same second (the system's own connectivity check); the other SYNs were the operator's browser to port 4001 and vertex's own loopback polling of `127.0.0.1:8081`. No DNS or SSDP query came from the scan. **Limits:** one device, so only the scripts that device triggers (SSH, SMB, RDP, NSCA) were exercised; the run produced no script-based finding, so it does not show that the scripts printed anything; the capture filter saw TCP SYNs and three UDP ports only; nmap here is 7.94SVN while the script list was checked against 7.99. **Trap in the runbook:** a full-network audit cannot be used for the tcpdump step, since every address is a legitimate target.
- 2026-10-29 (busy state, build): a disabled `<fieldset>` around the report turns off every native button inside it in one place, so a new button cannot be forgotten; the cost is that the filter chips and the "Show ports" folds go off too during a run (a scan is minutes). The page learns a run started only by polling `is_running`, so the report keeps its own `starting` state from the click (released when the page reports the run, or after 20 s) or the buttons stay live for a poll. A rescan queued behind a run of the same audit is absorbed as the plain audit (13.A trap), so the banner says "A scan is running" rather than promising the device.
- 2026-10-29 (file import, build): a file body must be resendable for the passphrase prompt of a step-up route (`httpClient.canResend` now accepts a `Blob`, not only strings) or the request fails with `reauth_required` and no prompt. The server reads a request for 30 s (`ReadTimeout`), too short for a 40 MB file over a slow link, so the import handler extends its own read deadline (`SetReadDeadline`, 10 min) and still caps the body. An import takes the same single job slot as a download (`running` + `importing`), so `Cancel` must not call a nil cancel func and `Clear` returns busy.
- 2026-10-29 (TLS hygiene probe): `nmap ... --script ssl-cert -p 22,4001,8081` against vertex.local printed only `fingerprint-strings` (the llama.cpp port); no port there speaks TLS, so a TLS hygiene check cannot be judged from vertex. Needs a device that does, run for real.

- 2026-10-29 (deep check, first live click, vertex v0.23.0): the owner ran it on `192.168.50.60` at 18:18 UTC; the stored result (`GET /admin/api/netaudit/deep`) holds one finding, `ssh_password_login` (medium, port 22), and the ports it judged: 22 answered as SSH, 4001 and 8081 answered neither SSH nor TLS (so nothing to judge there, as designed). The page showed it under the device at once. Carry-over confirmed the same evening: a one-device rescan of the device at 18:43 UTC put the finding into the report as an ordinary check finding, evidence "(from the deep check of 2026-10-29)", and kept the other seven devices (`devices_up` 8).

- 2026-10-29 (auditor assessment, root cause): the model wrote "first scan, no baseline" under a report whose code-written part had compared with the scan before. The prompt asked it to say "what is new or changed" and "if nothing is new or changed, say so", but the comparison is made by `RunReporter` after the run and is never in the tool result, so it had nothing to base the sentence on. **Lesson:** do not ask the model to describe data it is not given; tell it the code owns that part. A fix to a built-in profile reaches every workspace; a fix to a task template does not reach existing automations (their task file is a copy).

- **Tried:** Verifying the deployed v0.24.1 on vertex with two audit runs (2026-10-29; first with the abliterated Huihui Qwen3 30B, then `Qwen3.6 35B A3B`; UI seen by the owner, not by the agent) → **both runs finished and compared with the previous scan (`first_scan` false, deep finding carried as "(from the deep check of 2026-10-29)", accepted findings kept, no "first scan" wording); the abliterated model's assessment invented services (NFS/Telnet on a host with no open ports, Redis/MongoDB/Memcached, "SMBv1 reported by the checks"), Qwen3.6's named only services in the scan**. **Lesson:** the product passes; the assessment's honesty depends on the model, so judge an audit's model by reading its assessment against the Observed table.
