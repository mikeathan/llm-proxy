# Network module: a home-network security view with history, stats and low strain

**Status:** active (2026-10-31). Approved by the owner, including the SPEC-003 change. Phases 1 to 5 are built (v0.29.0, branch `network-module-history-and-page`, one PR); Phase 6 is dropped; Phase 0 is done except the captures noted below.
**Related plans:** [`network-detection.md`](network-detection.md) (the inventory, presence check, port checks, UPnP and decoys this module presents and builds on; its Remaining Work stays there).
**Origin:** the owner (2026-10-31): the network audit has grown past one automation into a security feature of the platform; it should watch the network continuously without straining the device or the network, show useful stats, and add the easy missing pieces. Other automations must keep working unchanged.

## 1. Goal and non-goals

**Goal.** A top-level **Network** page that answers, at a glance: *is my network as I left it, what needs a look, what changed lately* — backed by the data the audit already collects, a small bounded history for stats, and a few cheap passive additions.

**Not in this plan:** new scan types that need root (OS detection, UDP), vulnerability-script packs, credential guessing (Constitution II.3), exploit frameworks, packet capture or mirror ports, Wi-Fi monitoring, DNS phoning home (stays with AdGuard Home), IPv6 scan scope, TLS hygiene checks (parked until a second TLS device is captured). No other automation, workspace or connector behaviour changes.

## 2. What exists (verified 2026-10-31)

- The inventory is a snapshot: `models.DeviceInventory` (`backend/models/device_inventory.go`) holds devices, recent `Changes` that are dropped after a while, and the gateway state. **There is no time series**, so device counts over time, findings over time and time-to-fix cannot be shown today.
- The presence check (`netaudit/presence.go`: `Run`, `Tick`) sweeps, refreshes the inventory and alerts; it is the one frequent job and the right place to hang cheap sampling.
- The UI lives in two places: `components/settings/NetworkScanSettings.vue` (Settings) and `components/AgentIde/automation/AutomationDetails.vue` (the audit automation's page, which mounts `components/netaudit/*`). There is no `/network` route (`frontend/src/router/index.ts`).

## 3. Design decisions (the owner delegated these)

1. **A new route `/network`**, a main destination beside Automations, with tabs *Overview · Devices · Findings · Timeline · Settings*. The cards that exist (`DevicesCard`, `DecoysCard`, `FindingsReport`, `VulnDataCard`, the scan settings) move into it unchanged in behaviour.
2. **The audit automation stays** (it is the scheduler and the run record). Its detail page keeps the run controls and history and gains a one-line banner with the scan summary and an **Open Network** link; the cards leave it. Settings → Network keeps a single pointer to the module. No other automation page is touched.
3. **Stats come from a new bounded rollup store**, written by the presence tick and the audit run, never from scanning more.
4. **Nothing probes more often or more widely than today.** New probes are single packets to devices already known, for devices that lack a name, with a per-device back-off.

## 4. Strain budget (applies to every phase)

- No new periodic sweep. The presence tick (existing cadence) gets one more *in-memory* step: record counts.
- Naming probes: only unnamed devices, at most 4 in flight, one datagram per protocol, each device retried no sooner than 7 days after an answer and with doubling back-off after silence.
- A **strain guard** in front of the optional work (naming, change report): skip the cycle while a scan runs (`ErrScanBusy`), or while the host is under load, and say so on the page.
- Storage is bounded: daily rollups for 400 days, an event log capped by count, written at most once per tick, atomically.
- Every goroutine has a `ctx`, every timer is stopped, every map is bounded; the frontend polls one overview endpoint only while the tab is visible and the route is open.
- **Measured before merge** in each phase (not claimed): heap before/after a 24 h soak on the dev backend, tick duration, bytes on the wire for the naming probes.

## 5. Phases

**Phase 0 — evidence spikes (before building on them).**
- (a) Can a rogue-DHCP check run unprivileged? Listening for a DHCP offer needs UDP port 68, a privileged port; expect to drop it unless a capability is acceptable. *Accept:* a recorded yes/no with the exact error. **Partial (2026-10-31):** on the macOS dev machine an unprivileged process binds UDP 68 without error, which says nothing about Linux; **Done (2026-10-31, owner's paste from vertex):** `/proc/sys/net/ipv4/ip_unprivileged_port_start` is `1024`, so an unprivileged process cannot bind UDP 68 there (Linux rule for ports below that value; a bind was not attempted on vertex), and a DHCP client on the same host would hold the port anyway. **Phase 6 (rogue DHCP) is dropped** unless the owner accepts a privileged-port capability, which this plan does not recommend.
- (b) Which passive name sources answer on the owner's network: mDNS (`224.0.0.251:5353` unicast-response query), NetBIOS node-status (UDP 137), SSDP `friendlyName`. *Accept:* a real capture per source with hardware addresses and names stripped (ADR-0007), owner-approved one request at a time. **mDNS done (2026-10-31, owner ran one unicast query on vertex against one Mac):** a reverse PTR question sent to `<ip>:5353` from an ordinary source port was answered at once (87 bytes, authoritative, TTL 10) with the device's `<name>.local`, so no multicast and no privilege is needed; the real name contained a person's name, so the fixture `netaudit/names/testdata/mdns_ptr_response.hex` has it replaced by `example-laptop`. **Second capture (2026-10-31, same probe):** a Samsung device at 192.168.50.63 answered (71 bytes) with the name `Samsung.local`, only the brand, so an answer can be true and still not tell the operator which device it is; the Google box (192.168.50.188) gave no reply in 2 s. So of three devices two answered, and the suggestion must be offered as a hint, never as the device's identity. Fixtures: `mdns_ptr_response_tv.hex` (as captured: it holds no hardware address and no personal name). **Correction (2026-10-31):** the owner thinks 192.168.50.63 is their Samsung TV, not a phone (owner's belief, not verified against the router), so this is the TV result and the fixture is `mdns_ptr_response_tv.hex`; the owner is certain their phone is 192.168.50.127, which gave **no reply in 2 s on three runs while the phone was locked, and answered at once once it was unlocked** (run from the owner's Mac, not vertex; the owner accepts that as valid evidence): 93 bytes, flags `0x8400`, **transaction id 0 instead of the one sent**, one PTR answer with TTL 120 and a generic name `Android_<8 characters>.local`, plus an NSEC record. Fixture `mdns_ptr_response_android.hex` has those 8 characters replaced by `EXAMPLE1` (same length). The parser refused this real answer until it accepted id 0. Printers are not yet probed. **NetBIOS is skipped (owner, 2026-10-31: no Windows PC or NAS to test against), so it is not built;** SSDP beyond the router's own page is still to capture. Phase 3 starts with mDNS only: `netaudit/names` has the question builder, the answer parser (transaction id, response flag, owner name and bounded compression pointers checked) and `Clean`, tested against the fixture and hostile input.
- (c) An end-of-life data source and its licence. *Accept:* a named source and licence, or "no source: skip Phase 5". **Done (2026-10-31):** endoflife.date, repository licence MIT (its product descriptions are CC BY-SA 3.0 and are not imported); a public API exists but is documented as beta with possible breaking changes, so the data would be imported offline like the vulnerability data (ADR-0011), not fetched at scan time. The unproven part is mapping nmap product names to its product slugs; Phase 5 would cover only the few products where that mapping is exact.

**Phase 1 — history and stats backend.** A rollup store (`netaudit/history.go`) and `GET /api/network/overview` returning posture (counts by severity, unnamed devices, devices never scanned, last scan, last presence check), 30/90-day series, and recent events. TDD with fake clocks. *Accept:* store stays bounded under a 10 000-tick test; the endpoint is one read with no probe. **Built (v0.29.0):** `netaudit/history.go` (daily counts, 400 days, written only when a day's numbers change), fed by `Inventory.WithObserver` (every saved look) and `RunReporter.WithHistory` (every saved audit); `netaudit/overview.go` and `GET /admin/api/netaudit/overview` (`docs/api-reference.md`). The bound is tested with 450 days, not 10 000 ticks, because one day is one entry however many ticks it holds. **Measured:** a write plus read of the full 400-day file, 7.5 ms and 315 KB allocated (`BenchmarkNetworkHistory_WriteAFullYear`, dev machine, 200 runs); it happens only when a day's numbers change. **Not built:** the capped event log of §4; the "recent changes" list is derived from the inventory (new devices in 14 days, address changes), so no second record exists. Phase 4 adds a log only if its digest needs one.

**Phase 2 — the Network page.** Route, navigation, tabs, Overview (a posture line, four stat tiles, two small inline-SVG trends, "what changed" list), the moved cards, the automation banner and Settings pointer. No chart library. Simple/Advanced stays. Mobile first. *Accept:* `npm test`, `npm run build`, `npm run test:visual`; the automations list and a non-audit automation page are byte-for-byte unchanged in behaviour (test). **Built (v0.29.0):** `/network` with Overview, Devices and Findings tabs; Settings → Network scan keeps what may be scanned (so every existing deep link still works) and the devices card and decoys moved to Network → Devices; the audit automation's page gains a pointer banner; SPEC-003 2.21. Visual tests: 124 pass (the devices and decoys specs now open `network/devices`; a new `network.visual.spec.ts`). **Deviation:** the plan listed a Settings tab; it was not added, because a second copy of the scan settings would break "one path per job" and every `toSettings('network-scan')` link. The non-audit-automation unchanged check is by construction (the only changed automation file is `AutomationDetails.vue`, whose banner renders under `isAudit`), not a new test.

**Phase 3 — device naming suggestions.** Passive/unicast name sources from Phase 0(b) feed a *suggested name* shown on the Devices card with one tap to accept. Names are untrusted: length-limited, control characters stripped, never placed in an alert or finding (alert wording stays fixed). *Accept:* fixtures from real captures; a hostile-name test; probe budget test. **Built:** `netaudit/names` (question, parser, `Clean`, `Prober` over the guarded dialer, `Suggester` with at most 4 in flight, 32 per look, 512 entries, a 7-day retry after an answer and 6 h doubling to 7 days after silence), `device-names.json`, `PresenceDeps.OnLook` (one place, `lookHooks` in `app/netaudit.go`), `suggested_name` on the device list, the suggestion line on the Devices card. **Security decision:** naming a device approves it, so a suggestion on a new, unapproved device is information only ("check it is yours first") and the one-tap **Use this name** appears only once the device is approved. A stray device could otherwise get itself approved by announcing a friendly name. Candidates are checked against the declared scan scope (`scopedAsker`) on top of the guarded dialer. NetBIOS not built; printers and TVs unprobed. **Revised after review (owner, 2026-10-31):** naming used to run inside the presence look *before* the alert, so a slow pass (up to about 16 s on a first look with many silent devices) delayed an alert. Rather than add a background goroutine (single-flight, its own cancel and shutdown: more leak surface than the problem deserves), `Presence.Tick` now sends and marks the alert first and runs `OnLook` after, and still runs it when no connector can take the alert. A switch, **Suggest names for devices** (`DeviceNamesOff` in `NetauditConfig`, a negative flag so that nothing stored means on; `GET/PUT /admin/api/netaudit/device-names`), stops the questions and hides what was learned.

**Phase 4 — weekly change report.** A digest built from the rollups and inventory: devices added/gone, ports opened/closed, findings opened/fixed. Sent through the existing notify path, no new probes. *Accept:* golden test; sends once per week; off by default setting in the module's Settings tab. **Built:** `netaudit/digest.go` (`DigestMessage`, `WeeklyDigest`, `SummaryConfig`), `weekly_summary` in `NetauditConfig`, `GET/PUT /admin/api/netaudit/weekly-summary`, a switch on the Overview. It sends counts in fixed words (no device name or address; tested), once a week, only after a successful send marks it done, and only while the presence check is on, because it rides on a presence look. **Deviations:** the switch is on the Overview, not in a Settings tab (see Phase 2); the summary says devices known, new, not seen and unnamed and findings open now against a week ago, but not ports opened or closed, because no per-scan record of ports is kept and building one was left out.

**Phase 5 — end-of-life software finding** (only if Phase 0(c) names a source). One new finding from versions `-sV` already reports, with a fix-guide entry. *Accept:* fixture-based test; no new network request at scan time (data imported like the vulnerability data, ADR-0011). **Built differently:** `netaudit/eol.go` reads the CPEs nmap already prints, so the mapping the plan called unproven is exact (vendor and product from the CPE), and a short reviewed table in code replaces an imported dataset. Verified 2026-10-31 against endoflife.date (read through the fetch tool's summary, not the raw JSON): Apache httpd 2.0 and 2.2, PHP 5 to 8.1, OpenSSL 1.0.2 to 1.1.1, MySQL 5.5 to 5.7 and PostgreSQL 9.6 to 13. Left out on purpose: OpenSSL 3.0, MySQL 8.0 (ended 2026-04-30, not added) and anything a distribution routinely keeps patching. Medium, low for a distribution build. The cost: the table ages and each addition needs a date and a test. Not exercised on a real capture: no scan result with an end-of-life CPE exists yet, so the CPE shape rests on the existing `known_vulns` fixtures.

**Phase 6 — rogue DHCP:** dropped, see Phase 0(a).

Each phase is its own branch and PR with a minor version bump. Per phase: backend `go build ./... && go test ./... && go run ./tools/check-complexity/`; frontend `npm test && npm run build`; `./scripts/check-agent-harness.sh` after docs.
