## Fix branch `radio-fix-missing-routes` (2026-11-15, from `origin/main` at fe630e50; uncommitted; not run on vertex)

**What the owner saw after deploying v0.91.0:** clicking a dot gave `no route GET /admin/api/radio/air/track/9714bc3d`; "Yes, this is mine" on a network gave `no route POST /admin/api/radio/networks/<64 hex>/confirm`. **Cause:** the core's `stackRequest` puts the path *as requested* in `Request.Path` (the id is a path value in `Params`), but `Stack.Handle` and `handleAir`/`handleDevices` looked the route up by the *declared pattern* (`.../track/{id}`), so every wildcard route answered "no route". The tests all passed `Path: TrackPath` (the pattern), which no real request ever sends, so the bug could not show. Removing an owner device (`DELETE devices/mine/{id}`), calibrate and "Not mine" had the same fault.

**Fix:** `routePattern` in `stacks/radio/radio.go` maps the requested path back to its declared wildcard route at the top of `Handle` (a fixed route such as `devices/mine/presence` wins over `devices/mine/{id}`, as in the core's router). The test helpers `call` and `trackOf` now send the concrete path as the core does, plus `TestRoutePatternMapsARequestedPathBackToItsDeclaredRoute`. Checks run: `cd stacks && go test ./radio` (pass); `backend` `go build ./...`, `go test ./internal/app/ ./internal/transport/...` (pass), `go run ./tools/check-complexity/` (no new debt). **Not run:** the whole backend `go test ./...`, the harness check at the time of writing, anything on vertex. **Left:** the owner redeploys and clicks a dot and "Yes, this is mine"; bump `VERSION` (patch) at commit time, nothing is committed.

## Built: disk track and the "What is kept" panel (v0.91.0, same branch, not run on vertex)

**ADR-0055 (accepted 2026-11-15)** narrows ADR-0053's "nothing finer than a day" for one case: a per-cycle signal track on disk, **off by default**, `track_hours` 0, 24 or 48 (48 is a ceiling in code). The track route reads the disk when the setting is on, else memory; points carry `at` (unix) and `run` (a gap of more than 2.5 cycles starts a new run). Tests: default stores nothing, on writes and answers after a restart, off deletes, delete keeps the setting, forget deletes, refusals, age and row cap, and the file holds no neighbour address.

**UI:** a **What is kept** panel on the Listening tab (`RadioKeeping.vue`): one choice (Off, 24 hours, 48 hours), what is stored with Delete stored tracks, and **Forget the neighbours moved here from My devices**. The chart under a chosen dot is time-based.

**Bug fixed in the same branch:** opening "Comes and goes", "Outside your walls" or "Passing by" blanked the whole Neighbourhood panel in Advanced. **Around you restructured (same branch, v0.91.0):** one status line (listening with the time to the next reading and how far the sorting has got, or "not listening" with the way to start), things to look at, **one radar and one device list** with filter chips that carry counts (All, Yours, then each kind that has devices), a chosen device opened below (kind and why, the waiting progress, signal, last heard, the distance-over-time chart, Calibrate for the owner's device, Advanced adds cycles heard, retries, channels, first heard), the notes folded into one **How to read this** disclosure, and Airwaves as before. **Retention was never running (found and fixed in this branch):** `Store.Prune`, the daily job ADR-0053 describes, had no caller outside tests, so the 14 and 30 day limits were not enforced in the service. `pruneIfDue` now runs it (and the track age) at most once an hour from a run start and any Radio page read, `Store.Prune` also deletes any track point older than 48 h, and changing the track from 48 to 24 prunes at once. Tests: nothing outlives 48 h with nothing listening, and 48 to 24 prunes.

**Does listening run on a schedule? No, and by design.** A run is started by hand for at most 12 hours under a bounded session held in the core's memory (ADR-0054, I.17); a restart ends every session; nothing starts a run again. The Listening tab now says so. Recurring or always-on listening would need a **standing approval that survives a restart and outlasts 12 hours**, which is a change to I.17 and ADR-0054 and so needs the owner's decision: options are (a) a daily window the owner confirms once a day, (b) a longer session limit (still bounded, e.g. 7 days, still memory-only) with a reminder before it ends, (c) a persisted approval that the owner renews with the passphrase every N days. Not built.

## Traps found in this session

- **The jail refuses `socket(AF_UNIX)` to every child**, and `iw dev <name> ...` resolves the name with `if_nametoindex`, which opens one, so a jailed `iw dev X set type` failed with `No such file or directory (-2)` while `iw list` and `ip` worked. Fixed for the fixed `ip`/`iw` steps only (`Helper.step`); the `radio-listen` program keeps the refusal. Any new jailed program that resolves an interface name will hit this. To tell a unit property from the helper's own jail, run the same steps unjailed and under `systemd-run -p ...` with the unit's properties.
- **A squash-merged branch is gone from your history's point of view:** a PR merged while you were still pushing leaves the later commits out of `main`. Check `gh pr view <n> --json state` before pushing more to a branch, and cut a fresh branch from `origin/main` (cherry-pick) when it merged.
- The helper's status read only the net unit's gates drop-in, so radio actions showed "not installed" (fixed: `readAllHelperActions`). Each class has its own `llm-proxy-helper-<class>@.service.d/10-gates.conf`.
- macOS `sed -i` needs a suffix and a failed `sed` in an `&&` chain silently skips what follows: edit with Python or the Edit tool. Run `stacks/*` tests with `GOWORK=off` from the folder. `stacks/radio` is not in `go.work`.
- The scheduler test cannot advance a fake clock during `Run`, so the wait between cycles is the nominal `cycle - channels x window` (the real run does include setup time; a cycle is a little longer than its setting).
- A stack route that declares no `Action` and no step-up is safe to start a run because the core serves the helper request only under an open session; do not add a grant path to the run.
- A chained `git switch && cherry-pick && push && push --delete` was refused by the auto-mode classifier; run git steps one at a time.
- `radio_listen`'s raw bytes are never returned to the browser (`keepsToItself`); the answer is the parsed summary. No service parser exists yet, hence the `parse_error` above.
