# Constitution (The Law)

This document defines the immutable architectural and security laws of the project. All code must adhere to these rules without exception.

## I. Network Security (The Guarded Hull)

1.  **No Raw Sockets**: No code is permitted to instantiate a raw `http.Client`, `http.DefaultClient`, `net.Dial`, or `net.DialContext` for external or LAN communication.
2.  **Mandatory Guardrails**: All network interactions must pass through the `NetworkTools` abstraction.
    *   **Agent Tools**: Must use `network.FetchURL` or `network.HTTPClient()`.
    *   **Infrastructure**: Must use `network.DialContext()` to ensure DNS rebinding protection and boundary checks (LAN vs Internet) are applied at the socket level.
    *   **Provider Infrastructure Carve-Out**: Inference proxy traffic, provider catalogue listing (`ListModels`), local serving-context probes (`/slots`, `/v1/props`, `/api/v1/models`), and provider connection tests use the dedicated shared pooled client injected through the `providers.HTTPDoer` interface (`proxy.SharedTransport`, 45s timeout; 5s child context for local probes). This client never carries agent-tool guardrails — it is a distinct traffic class. Agent-tool network guardrails remain unchanged and mandatory. No raw `http.DefaultClient` / bare `http.Get` is permitted anywhere; provider infrastructure must go through the injected doer.
3.  **Boundary Enforcement**: The system must strictly distinguish between LAN access and Internet access. Tools must verify destination safety before the first byte is sent.
4.  **Inbound Webhook Exemption**: Inbound HTTP handlers that receive messages from external platforms (webhooks, callbacks, bot API requests) are exempt from §I.1–I.3. They use standard `net/http` handlers and require no `NetworkTools` wrapper. The exemption applies only to receiving incoming connections — any outbound network call triggered by the handler (e.g. replying to a Telegram message) must still pass through `NetworkTools`.

5.  **The Control Plane Is Authenticated** (added 2026-10-30, plan `admin-api-authentication`; its design records the threat model and the security review). Everything under `/admin/api/` can run code as the service user, change what the agent may do, or erase the data root, so it answers only to a credential, and every surface that does not is **named in an allowlist**:
    *   **Default deny.** A request to `/admin/api/*` needs a session cookie or an admin script token, decided from the path by one middleware (`api.Authenticate`), never per handler. While no passphrase exists nothing can be signed in, so the admin API answers only the allowlist below (`401 setup_required`). `/v1/*` needs an inference key once one exists. A sign-in store that cannot be read refuses (`503`); it never reads as "sign-in off".
    *   **The allowlist** is: the UI shell and its assets (they hold no data), `GET /admin/api/auth/status`, `POST /admin/api/auth/{login,setup,logout}`, and `/api/v1/webhooks/{connector}`, which carries its own mandatory secret (a connector without one refuses every call). A route test classifies every registered route and fails on one that is in none of these classes, so a new route cannot be open by accident.
    *   **Credentials are stored as hashes** (the passphrase with argon2id; tokens and session ids with SHA-256), in a file only the service's account can read, outside every workspace. A secret is never logged and never printed at start. The one-time setup code is made only by the command line on the server, as the server's OS user.
    *   **Destructive actions ask again.** Wiping data, factory reset, the sandbox and terminal switches, stored secrets, MCP servers, new tokens, a longer session, a deep check of a device (an intrusive run), and a settings save that changes what the model server runs need the passphrase confirmed shortly before (step-up). A script token can never do these.
    *   **Browser protection** applies to `/admin/` whether or not a passphrase exists: an accepted `Host`, no cross-site request (Fetch-Metadata, then Origin), framing and sniffing headers, and no wildcard CORS.
    *   **Sign-in is compulsory** (amended 2026-10-30; it was open until a passphrase was set, with a banner). The first passphrase is set from the one-time code the server's command line makes, and until then the interface shows only the setup page. A new install listens on this machine only. `/v1` keeps its own rule (an inference key, once one exists) and is a separate decision.

6.  **Decoy Listeners** (added 2026-10-30 with plan `network-detection` Phase 5; in force since the owner merged the security review below). I.4 exempts inbound handlers for external platforms; this item allows one more inbound surface, the decoy services of `core/netaudit/decoy`, and nothing else, on these terms:
    *   **Off until the operator turns it on**, and turning it on or off is a step-up action (`PUT /admin/api/netaudit/decoys`). Switching off closes every socket. A host that cannot bind a port says so; it never retries into another.
    *   **A fixed table of ports in code** (`decoy.Specs`): unprivileged, never configurable by the operator or a model, and in neither of the scan port lists, which a test pins, so the audit's own scans of the host never touch a decoy.
    *   **Low interaction.** A connection is read for at most 64 bytes under a deadline and the bytes are discarded; the only thing ever sent is a fixed short string from the table. Nothing a peer sends is parsed, stored, logged, forwarded, shown to a model or executed, and a connection never causes this program to open another.
    *   **Only who, which decoy and when is kept** (source address, decoy port, count, first and last time; at most 200 entries). A source counts only if it is inside the declared scan networks and not one of this computer's own addresses, so the host's own audit and sweep never look like an intruder.
    *   **Bounded.** At most 16 connections at once (the rest are closed at once), one connection per source per second per decoy, and a deadline on every read and write.
    *   **Alerts are counts, fixed words and the source addresses** to the operator's connectors, sent at most every five minutes and marked as told only after they were sent. (Amended 2026-10-30 at the owner's request: the first version was counts only, and the owner could not tell which device it meant.) The address is the connection's remote address as the operating system reports it for a source already inside the declared scan networks; it is not bytes the peer sent, and it is the only per-device text in the alert (no banner, no payload, no name). At most five addresses are listed and the rest are counted. A touch is a finding in fixed wording; the model never sees one.
    *   **Residual risks, accepted:** any device on the network can open a connection and so can use up the 16 slots for a moment (the limit is the defence); a host firewall can hide the decoys (the screen says so); the SSH banner may attract scanners (that is its purpose). A change to the table of decoys is a security review.

7.  **Link-Local IPv6 Discovery** (proposed 2026-10-30, plan `network-detection`, ADR-0016; it is in force only when the owner merges the pull request that carries this text, which is the owner's approval of the security review below). I.1 to I.3 send LAN traffic through `NetworkTools`, which has no way to send an ICMP packet; this item allows one more outbound packet, sent by `platform/neighbors.Discover6` and by nothing else, on these terms:
    *   **Off until the operator turns it on** (`PUT /admin/api/netaudit/ipv6-discovery`; an ordinary signed-in request, because it sends one fixed packet and opens no listening socket). Switching it off stops the packets at the next look.
    *   **One fixed packet.** An ICMPv6 echo request to the link-local all-nodes group `ff02::1` with a hop limit of one, built in code and never shaped by an operator, a model or a device. It is sent at most once per network interface per look (a presence check or an audit), on at most eight interfaces, and only on an interface that is up, multicast-capable, not loopback, and holds a device inside the declared scan networks. Nothing is sent to a routed or global address.
    *   **No privilege is asked for.** The packet goes through the kernel's unprivileged ICMP datagram socket, which the host allows or refuses through its own setting (`net.ipv4.ping_group_range`). The program never requests a capability, never opens a raw socket, never starts a program for it, and never works around a refusal: a refusal is a stated problem on the screen with the one-line change the operator may make.
    *   **Replies are never read.** The socket stays open for at most two seconds and is closed. The only effect is on the kernel's neighbour table, which is read exactly as before (netlink, no packet, no program); nothing a device sent is parsed, stored, shown to a model or put in a message.
    *   **The scan scope does not change.** No IPv6 address is scanned, probed or connected to; devices found only over IPv6 are listed and reported like those the table already held, with no finding keyed by an IPv6 address. II.3 item (3) stands as written.
    *   **Residual risks, accepted:** every device on the link sees the echo, as it sees any ping; Wi-Fi multicast is slow and lossy, so a quiet device may not answer; and a host setting that the operator loosens (`ping_group_range`) lets other local accounts send pings too, which the screen says.

8.  **Router Log Listener** (proposed 2026-11-01, plan `network-security-roadmap` Phase 4, ADR-0018; amended 2026-11-04 to let its firewall lines be counted, plan `network-attempts-integrity-timeline` P2, the owner having approved the design; amended 2026-11-05 to let its DNS query lines be read, plan `stack-modules-and-new-detection` P3, the owner having approved the text; in force only when the owner merges the pull request that carries this text, which is the owner's approval of the security review below). I.6 allows the decoy sockets and nothing else; this item allows one more inbound surface, the UDP socket of `core/netaudit/routerlog`, on these terms:
    *   **Off until the operator turns it on**, and turning it on or off is a step-up action (`PUT /admin/api/netaudit/router-log`). Switching it off closes the socket. A host that cannot bind the port says so; it never retries into another.
    *   **One fixed unprivileged port in code** (`routerlog.Port`, 5514), never configurable by an operator, a model or a device, and never one of the decoy, scan or service ports (a test pins it). The router's own setting stays at 514; the operator redirects 514 to this port with a firewall rule the screen shows and the program never runs.
    *   **Only the default gateway is heard.** A datagram from any other address, and every datagram while the gateway is unknown, is dropped before it is looked at. Lines that cannot be one of the two device messages (the firewall lines, which are most of the log) are told apart by one search of the start of the line and use none of the device allowance, and are counted as the next item says; of the others at most ten a second are looked at, each at most 1,024 bytes, and the rest are dropped unread. The socket's receive queue is 64 KB, so what arrives faster than it is read is dropped by the kernel and memory use does not depend on what is sent.
    *   **Two message shapes, one fact.** Only an acknowledged DHCP lease and a Wi-Fi association of the router's stock firmware are recognised, each by an exact shape. What is kept of a datagram is the kind and the hardware address in it, and, for a lease, the device's host name when it is a plain one (letters, digits, dot, hyphen and underscore, at most 63 characters), for the length of one call. That name goes to one place only: the name suggester, which cleans it and offers it on the Devices card for the operator to confirm, only for a device the list does not know or the operator has not named, at most five devices in ten seconds and the same device and name once an hour. It is never put in a finding or an alert, logged, sent to a model or used as it came. The router's name, every address and every other word are dropped while parsing, and nothing else from a datagram is stored, logged, shown, put in a finding or an alert, sent to a model or executed.
    *   **Firewall drops are counted, never kept (amended 2026-11-04).** One more exact shape is recognised: the router's `kernel: DROP` line for a packet that came from the internet, meaning the inbound interface is named and the source is a public IPv4 address (not private, loopback, link-local, multicast or carrier-grade NAT; a packet from inside the house is not counted). What is kept of such a line is its protocol (`tcp`, `udp`, `icmp` or `other`) and, for tcp and udp, its destination port, for the length of one call. They go to one place only: a counter in `core/netaudit` that holds a total and a table of at most 256 ports in memory and, every five minutes, adds the total and the ten busiest ports to the day's entry of the Network history. The sender's address, the router's name, the hardware addresses and every other word are dropped while parsing, so no address and no line of the log is stored, logged, shown, put in a finding or an alert, sent to a model or executed. Parsing a drop is a few dozen string operations and is not held to the device allowance; the socket's 64 KB queue bounds how many arrive, and a scan of every port cannot grow the table. The counts are shown as figures only (a stat on the Overview, a card and a row on the Timeline) and, as numbers, may be named in the Timeline summary's prompt; they never raise a finding or an alert, because the log is unauthenticated UDP and a forged line can change a number and nothing else.
    *   **DNS query lines are read for the names devices ask for (amended 2026-11-05).** One more exact shape is recognised from the default gateway, `dnsmasq[pid]: query[TYPE] name from address`, by one search of the line, under its own counter and limit and never the device allowance, so a burst of them cannot starve a lease or a Wi-Fi line. What is kept: the device's hardware address (taken from this computer's neighbour table, never from the line), the name if it is a plain DNS name (letters, digits, hyphen, underscore and dots, in lower case, at most 253 characters), and the time. Dropped while parsing: every other word, the router's own and this computer's lookups, and every reverse lookup. The names go to one place only: the phone-home watch (`core/netaudit/phonehome`), which keeps at most 256 devices, 512 names a device and 32 recent times a name in memory and in one file. A name is shown as text only, named in a finding or an alert in fixed words, and is never logged, sent to a model or acted on. It never raises more than a finding to review: any device on the network can forge a line, so a forged one can cause a false hint and nothing else. **Encrypted-DNS names are told as a hint (proposed 2026-11-06, plan `network-tls-dns-ssh-address-and-discovery`; in force when the pull request that carries it is merged).** A name that is, or lies under, one of a fixed list in code of public encrypted-DNS servers (`phonehome.encryptedDNSNames`) is compared with the names already kept, on this computer, and a device that asked for one lately is one finding in fixed words (it may be sending its lookups around the router); it is never a message, because Firefox and a phone's private-DNS setting ask for these names by default. Nothing more is read or kept, and nothing is sent. **The names are shown per device (amended 2026-11-11, plan `network-traffic-more-handoff` B1):** the Traffic tab's "Other devices" list reads the watch's memory (`GET /admin/api/netaudit/device-lookups`, an ordinary signed-in read) and shows, per device, the names it asked for grouped by the domain they sit under (found by the last labels of the name, with no lookup), newest first, at most 128 names a device, with the flags the watch already raised. Names are shown as text only, nothing is resolved from this computer, and the screen says these are lookups and not traffic. Switching the phone-home module on or off is an ordinary signed-in request, because it opens no socket of its own (the router log's socket, which is a step-up switch, is its need).
    *   **Failed router sign-ins and Wi-Fi disconnects are counted, never kept as lines (proposed 2026-11-06, plan `stack-modules-and-new-detection`, as captured on the wire that day).** Two more exact shapes are recognised, by one search of the line, under their own limit and never the device allowance: `HTTPD: [LOGIN][http][Web] failed (ADDRESS)` or `captcha error (ADDRESS)`, and `wlceventd: wlceventd_proc_event(N): IFACE: Deauth_ind MAC, status: N, reason: TEXT (CODE), rssi:N`. They are accepted from the default gateway and, because the router's mesh nodes send their own Wi-Fi lines, from any private address in the house, and from nowhere while the gateway is unknown. What is kept of a sign-in line is its kind; of a disconnect line, its kind, the reason code and the hardware address of the device disconnected. Dropped while parsing: the address that tried to sign in, the interface, the router's name, every other word, and a good sign-in is not read. They go to one place only: `core/netaudit.RouterWatch`, which holds in memory the times of the last five failed sign-ins and the last twenty disconnects, the times of at most 32 bursts of each kind for a day, and a count of disconnects for at most 256 hardware addresses for a day. When five failures fall within ten minutes, or twenty disconnects within one minute, it sends one message in fixed words with no address and no device (at most one of each kind an hour) through the alert log. The nightly report shows, as findings to review keyed by the router's or the device's address, a burst in the last day and a device with a hundred disconnects in a day, in fixed words and numbers. Because the log is unauthenticated UDP, a forged line can cause a message or a finding and nothing else; no line and no sign-in address is stored, logged, shown, sent to a model or acted on.
    *   **The malware host list is matched here and downloaded only when the operator asks (proposed 2026-11-05, plan `stack-modules-and-new-detection`; in force when the pull request that carries it is merged).** The names devices ask for are compared on this computer with the list of host names abuse.ch's URLhaus publishes as serving malware; no name a device asked for is sent anywhere. The list is fetched only when the operator presses Download, through the guarded network client, from an https address on abuse.ch that the operator saved. That address holds the operator's own key, so it is a stored secret (encrypted, `III.6`): it is set or removed by a step-up request, never returned, logged or put in an error, and used for nothing but that download. The list is bounded (at most 100,000 names, 8 MiB), every name is vetted like a name from a query line, and a failed or empty download keeps the list already held. A match is a finding and a message in fixed words, never an action.
    *   **Apart from counting drops, the only effect is to ask the presence check to look soon**, and only for a hardware address the device list does not know. The look is the one the check takes anyway, paced (a pause of a few seconds, never closer than a minute to the previous cycle, wakes merged), and the device list still comes only from this computer's own neighbour table. A forged datagram can therefore cause an early look or a larger count and nothing else: it cannot add a device, raise a finding or change an alert.
    *   **Residual risks, accepted:** any device on the network can make the check look early, at most once a minute, and can inflate or deflate the day's count of refused attempts (which is why it is a figure and not a finding); a device spoofing the router's address is not stopped by the address check (UDP has none stronger), which is why the effect is only a look; a host firewall can hide the port (the screen says so).

9. **Nearby Discovery** (proposed 2026-11-03, plan `network-nearby-discovery`, ADR-0024; the owner approved the design on 2026-11-03, and it is in force only when the owner merges the pull request that carries this text, which is the owner's approval of the security review). I.1 to I.3 send LAN traffic through `NetworkTools`, which refuses multicast and cannot read replies from many senders; this item allows one more socket, opened by `platform/mcast` and by nothing else, on these terms:
    *   **Off until the operator turns it on**, and turning it on or off is a step-up action (`PUT /admin/api/netaudit/nearby`). While off, no socket is opened and nothing is sent. The switch names both datagrams. It follows the Guardrails local-network switch: with that switch off the look does not run and the screen says why.
    *   **Two fixed datagrams, built in code**, never shaped by an operator, a model or a device: an mDNS PTR question for `_services._dns-sd._udp.local` to `224.0.0.251:5353` and an SSDP `M-SEARCH` for `upnp:rootdevice` to `239.255.255.250:1900`. At most once per interface per look, on at most four interfaces that are up, multicast-capable, not loopback and hold an address inside the declared scan networks. Hop limit 1; multicast loopback off; **no group is joined**, so no multicast datagram is ever received.
    *   **An ephemeral port, no privilege.** The socket is bound to the interface's own IPv4 address and an operating-system-chosen port, is open for at most five seconds, and is closed. The program never asks for a capability, never opens a raw socket, never starts a program for it, and never uses port 5353 or 1900 as its own.
    *   **Bounded reads.** At most 512 datagrams per look, 32 per sender, 4,096 bytes each; a 256 KB receive queue, so memory does not depend on what is sent. A datagram from any source that is not an IPv4 address inside the declared scan networks, is this computer's own address, or is on the blocked list is dropped before it is looked at. A look runs at most once every 30 seconds and one at a time (checked on the server, not only by a disabled button).
    *   **Typed parsing; everything a device sends is untrusted.** Only these survive parsing: the sender's address; service types matching `_[a-z0-9-]{1,15}\._(tcp|udp)`, at most 16 per device; port numbers from service records; a device type matching the UPnP URN shape; and names, maker and model cleaned and cut to 40 characters (`names.Clean`). TXT values, `SERVER` text other than a parsed version token, and everything else are discarded while parsing. Kept names are shown as plain text only; they are never put in a finding, an alert, a log line or a prompt, and findings use fixed wording.
    *   **Follow-ups are ordinary guarded connections to the replier's own address.** The UPnP description page is fetched only from the `LOCATION` that is on the replier's own address (the rule `upnp.ParseSSDP` already enforces), with no redirect, at most 32 pages, 256 KB each. Any later probe (the camera check) uses a fixed port table in code, never a port a device announced.
    *   **Web checks are ordinary guarded connections (proposed 2026-11-06, plan `stack-modules-and-new-detection`, ADR-0029; in force only when the owner merges this).** The web checks send plain `GET` requests, in this program's own process, to web ports that a scan found on addresses of the declared scan scope. The paths are a fixed list written in code (`core/netaudit/webprobe`); no redirect is followed, no proxy is used, and the scope's policy approves the address of every connection at the moment it is made. They are bounded: at most 64 services and 8 ports a device, one request every 200 ms to a service, 256 KB read from an answer and 8 s for a request. Certificates are not checked, because nothing secret is sent: the only headers are a fixed `User-Agent` and `Accept`, no credential is tried, no cookie is kept, and no listed path logs in, searches or changes anything. An answer is read only to see whether a fixed phrase appears; a finding says the check's own words with the address and port, never the device's text. They run in the operator's deep check of one device and, nightly, only while the operator has switched the module on (off by default, a signed-in step-up switch).
    *   **Certificate checks are ordinary guarded connections (proposed 2026-11-06, plan `network-tls-dns-ssh-address-and-discovery`; in force only when the owner merges this).** For each secure web service the scan found, at most 64 in all, the web checks make up to three TLS handshakes in this program's own process (one that offers current versions, and one each that offers only TLS 1.0 and TLS 1.1), to the service's own private address through the same approved dial, with a pause between services and between a service's handshakes, and a five-second limit each. The handshakes offer every cipher suite the program's TLS library knows, the broken ones included, because old devices often accept only those and would otherwise look silent; since nothing is sent, offering a weak suite exposes nothing. The handshake does not verify the certificate, because it sends nothing that a certificate would protect: it writes no application data, reads no answer, and closes as soon as the handshake ends. Only the certificate's start and end dates, whether it was signed by itself, and which old versions were accepted are kept; none of the certificate's text (names, issuer, subject) is shown, logged or sent to a model. A refused address is an error before anything is sent.
    *   **Silence is never absence.** A device that did not answer is "not heard", never gone, and no finding resolves because a look was quiet; a finding resolves only on a later answer that contradicts it.
    *   **Residual risks, accepted:** every device on the link sees both questions, as it would see any browser's; a device may answer with false claims, which at most produces a hint row or a finding worded "this device says it is…"; Wi-Fi multicast is lossy and an access point may block it, so a quiet look proves nothing (the screen says so); an unprivileged local account on this computer could read the replies of its own socket but not ours.

10. **Failed-Login Record** (proposed 2026-11-06, plan `network-tls-dns-ssh-address-and-discovery`, ADR-0030; in force only when the owner merges the pull request that carries this text, which is the owner's approval of the security review). I.1 to I.9 are about the network; this item allows the program to read one file of this computer, the system's record of failed logins (`/var/log/btmp`), on these terms:
    *   **One file, read only, by one package.** `platform/loginlog` opens that path read-only and nothing else in the program does. The service reads it only because the unit lists the `utmp` group (`SupplementaryGroups=utmp`), which under `ProtectSystem=strict` is read access to `btmp`, `wtmp` and `utmp` and nothing else; the `adm` group, which would expose `auth.log` and every other system log, is not used.
    *   **Off until the operator turns it on.** The module "Failed logins, this computer" is off by default. It opens no socket and sends nothing, so switching it needs no passphrase. While it is off no record is read; the module's readiness check only opens the file read-only, and closes it without reading a byte, each time the module list is read, to say whether the group is missing.
    *   **Only the type, the time and the source address of each record are read (amended, proposed 2026-11-09, ADR-0036 follow-up; in force only when the owner merges the pull request that carries this text).** Each record is 384 bytes (utmp(5)); the program reads the record type, the 32-bit time and the 16-byte binary source address (`ut_addr_v6`, at byte 348), and never the user name, the terminal or the host text the record also holds: those are written by whoever tried, so they can hold anything, including a password typed into the name field. The address is read as bytes and parsed into an IPv4 or IPv6 address; an all-zero field is no address. What may be shown is a count from this network and from the internet, a count with no address, and the three busiest source addresses with their counts, in the nightly finding of a burst only; an address is never put in an alert message, kept in a file or sent to a connector, and no name is ever kept, shown, logged or sent. At most the last 4,096 records are read (about 1.5 MB, however large the file is), newest first, stopping at the first one that is not newer than the time asked for. What the watch keeps is the time it last told the operator and the time it last read the file.
    *   **A burst is a number, never an action.** Ten failures within ten minutes raise one fixed-words message through the alert log (at most one an hour) and one nightly finding about this computer. Nothing is blocked, banned or changed. Only a program that may write the file can make a record, so a forged record needs the privilege the file already requires.
    *   **Every program the service starts has the group.** A supplementary group is inherited by agent shells and the terminal tool's children. With the Landlock filesystem jail in force their read list (`platform/sandbox/landlock_linux.go`: the workspace, system libraries, `/etc/ssl` and a few device files) does not include `/var/log`, so they cannot open `btmp`; where the jail is not in force (`Effective().Filesystem.Mechanism` is none) they can, and `wtmp` holds the user name and host of every successful login. That is a read of login history by a program the operator already lets run commands as this user, and is accepted for the same reason as the other readable system files.
    *   **Residual risks, accepted:** the record holds password failures, not failed key logins, so a guesser that only tries keys is not counted; a root user can edit or empty the file; a rotation of the file loses what the old file held.

11. **Privileged Helper** (proposed 2026-11-07, plan `network-stack-privileged-additions` section 2a, design `network-privileged-helper-design`, ADR-0034; the owner approved the decisions D1 to D9 of that design on 2026-11-07; in force only when the owner merges the pull request that carries this text, which is the owner's approval of the security review in the design section 2 and the ADR). The service runs with no capability and a filter that refuses Unix sockets to its children, so some network work (UDP scans, OS detection, a short capture of link-level headers) cannot run in it. This item allows one more process, a separate helper owned by the core, to do that work for the service on these terms:
    *   **A closed catalogue, in core code.** The helper does only the actions in a table in core code (`scan_udp`, `os_detect`, `capture_window` to start with). An action has typed parameters, a builder that makes the whole argument list itself and never forwards one it was given, a scope check and caps (time, bytes, rate). A stack, a manifest, a model or an operator cannot add an action; adding one is a code change that passes review.
    *   **Installed by the operator, off by default, three gates.** The unit files are installed by the operator with a root command (`scripts/install-helper.sh`), never by the service. One unit per privilege class, started on demand by socket activation, one short-lived process per request. An action runs only when its unit is installed, its per-action switch in the settings is on (a switch changed only with step-up, like the other privilege switches), and the root-owned drop-in the install step wrote lists it.
    *   **Only a step-up request asks.** A request to the helper is made only when a signed-in operator session at step-up level calls a route that declares the action (token principals are refused), and the core mints a one-use grant bound to that action and its parameters. A model, an automation or a stack never causes a call by any other path.
    *   **The helper decides who is calling.** It accepts a request only from the service's main process (the peer's process handle against the unit's `MainPID`), not from a group, uid, parent or cgroup, because children of the service share all three. It refuses everything else without detail. This holds only while a child cannot take over the main process: the install step and the helper both refuse while the host's `ptrace_scope` is 0 (Yama then lets a process inspect only its own descendants, and a child of the service is not its ancestor).
    *   **Two checks on where it may scan, neither trusting the caller.** The helper checks the target from its own fixed rules (one private IPv4 host as II.3 item 3 defines, a fixed port list, an interface that exists), whatever the service asks. The operator's declared scan ranges (Network settings) are enforced by the service before it asks: a target outside them, or any target while none is declared, is refused before the grant is used. The helper keeps no copy of the ranges, because a copy made by a root command would be taken from a file the service can write, and would only add a step the operator must repeat after every change.
    *   **Programs run jailed, untrusted data is parsed outside.** A program the helper starts runs under the same file confinement as II.3 requires, with arguments the helper built. What the program or the network returns is parsed in the unprivileged service, never in the privileged process; the helper returns bounded, typed records only.
    *   **A capture is time-boxed and headers only.** It opens a packet socket with a fixed filter (ARP, DHCP, mDNS, neighbour discovery), keeps at most 64 bytes of each frame, stops at a short window or a frame cap, never sets promiscuous mode and sends nothing. I.7 and I.9 say the program never opens a raw socket; that stays true of the service and its children, and this capture is the only exception, made by the helper.
    *   **The service refuses unless the sandbox is in force.** It makes no call unless `Effective()` reports file confinement and Unix-socket denial. That is a safety interlock for the service's own calls, not the control against a hostile child, which is the caller check above.
    *   **The scan scope does not change.** Nothing here widens II.3 item 3 or the declared scan networks.
    *   **Residual risks, accepted:** a compromised service process can mint grants and cannot be told apart from the real one, so what limits it is the catalogue, the helper's fixed scope rule and caps, the action list the install wrote, and the switches (it can ask the helper to scan any private host, which it can already do with the unprivileged scans it has); a kernel older than 6.5 has no race-free peer handle, so the helper falls back to the peer's pid with the reuse race stated; and the helper's unit holds `CAP_NET_RAW`, so a flaw in the helper itself is a root-adjacent flaw.
12. **Unicast UDP Service Probes** (proposed 2026-11-08, plan `network-nightly-udp-probes`; the owner approved the probe list and this text on 2026-11-08; in force only when the owner merges the pull request that carries this text, which is the owner's approval of the security review). I.2 sends LAN traffic through `NetworkTools`; the audit's TCP checks use it. This item allows two more fixed datagrams through the same guarded dial, sent by `core/netaudit` (the `udpchecks` package) and by nothing else, on these terms:
    *   **Off until the operator turns it on** (an ordinary signed-in request at step-up level, the module `udp_probes`).
    *   **Two fixed datagrams, built in code**, never shaped by an operator, a model or a device: an SNMPv3 engine-discovery message (no community string, no credential) to UDP 161 and an SSDP `M-SEARCH` for `upnp:rootdevice` to UDP 1900, each to one device's own unicast address inside the declared scan scope. Nothing is sent to a group, a broadcast or a routed address.
    *   **Bounded**: at most four devices in flight, 64 devices per look, a two-second wait, a 1,500-byte read, the socket connected to the device.
    *   **No privilege, no program, no helper.** The datagrams go through the ordinary guarded dial after a scan-scope check; no capability, no raw socket (I.7 and I.9 stand), no child process.
    *   **Replies are never trusted or shown**: only whether the device answered in the expected form is kept; silence is "unknown" and never resolves a finding.
    *   **Residual risks, accepted:** every probed device sees two datagrams and may log them; a device that only speaks SNMP v1 or v2c is missed; some cheap devices mishandle unexpected UDP (one datagram each, once per look).

13. **Host Traffic Look** (proposed 2026-11-09, plan `network-host-traffic-and-findings-ui`, ADR-0040; amended 2026-11-11, plan `network-clickable-findings-traffic-owners`, ADR-0043, to let the server name of a TLS ClientHello be read and the holder of an internet address be looked up in a table kept on this computer; the owner approved the design and these bounds on 2026-11-09, and asked for both amendments on 2026-11-11; in force only when the owner merges the pull request that carries this text, which is the owner's approval of the security review). I.11 allows a headers-only capture of broadcast and multicast frames, a fixed 64 bytes of four kinds of frame; this item allows one more helper action, `capture_host`, which looks at the traffic of this computer itself, on these terms:
    *   **On demand, step-up only.** Off until the operator switches the action on (a step-up switch, the third gate of I.11) and the install lists it; a press needs step-up and a one-use grant; no schedule, agent, automation or stack ever causes one. At most 12 presses an hour, 60 seconds each. `capture_window` keeps its own action, filter and 64 bytes; nothing here widens it.
    *   **One interface**, the default route's interface unless the operator names one that exists and is up; never promiscuous mode; nothing is sent.
    *   **A fixed filter, built in code.** IPv4 and IPv6 frames that carry TCP, UDP or ICMP, and nothing else. Of every such frame but a DNS message it keeps exactly the Ethernet header, the IP header and the first four bytes after it, which are the ports (38 bytes for IPv4 without options, 58 for IPv6, never more than 78): the addresses, the ports and the size, and not one byte of payload. Of a DNS message (UDP or TCP port 53) it keeps at most 512 bytes, because a name is in it; that is the one payload this item keeps. Every other frame is dropped by the kernel filter before the program sees it. **The first segment of a TLS ClientHello is the one other frame that keeps payload (amended 2026-11-11):** a TCP segment whose payload starts `0x16`, `0x03`, with a handshake type of `1` at its sixth byte, on any port, keeps at most 768 bytes of the frame (its headers included), because the server name an address was asked for is in the first few hundred. The filter finds the payload from the TCP data offset, reads nothing past the frame's end (a frame with fewer than six payload bytes, such as an acknowledgement, stays an ordinary frame), and never samples a hello away. Nothing else is kept of any other frame: a segment that is not a hello keeps exactly the headers and ports, whatever it carries. QUIC (whose hello is in an encrypted packet) and a hello over IPv6 with extension headers are not read.
    *   **Bounded without reading a frame.** At most 60,000 records and 8 MiB of output a window. Ordinary frames are sampled one in N by the kernel filter, N a power of two up to 1,024, which the capture program raises (never lowers) by doubling when it has kept more than 800 frames in a second, and writes in every record; a DNS message is never sampled away. A window that reaches a limit, or that cannot change its filter, stops and says so; it is never presented as complete, and a sampled window is shown as an estimate. The helper's response frame is 16 MiB for this reason; it is read only by the service, from the helper.
    *   **The helper parses nothing, and the browser never gets the bytes.** The unprivileged service reads the headers (I.11). It keeps no frame: it reads each record into counts, a table of at most 512 conversations and 256 names, and discards the bytes. The route's answer to the browser is the parsed summary or the reason there is none; the raw output is not in it.
    *   **Names are untrusted text.** Only a plain DNS name (the rule of I.8: letters, digits, hyphen, underscore, dot; lower case; at most 253 characters; no reverse lookup) is kept: from a DNS answer's question, for the addresses that answer gave, or (amended 2026-11-11) from the `server_name` host name of a ClientHello this computer sent, for the conversation that hello opened (a hello that came in names this computer's own server and names nothing). The service reads the hello's fixed fields with a bound before each read, walks at most 64 extensions, keeps the one vetted name and discards the bytes; at most 256 names are kept in all. A name is kept only to label a destination or a conversation on the traffic view, and the view says which of the two it came from. It is never put in a finding, an alert, a log, a prompt, a model summary or the Timeline, and nothing is sent to look one up.
    *   **Who runs an address is looked up on this computer (amended 2026-11-11).** The service may name the holder of an internet address (the network operator's own words, its AS number and a two-letter country) from a public-domain table of address ranges (IPtoASN, `iptoasn.com`). The table is downloaded only when the operator presses a button, which is a step-up action that says what it asks: two files, about 11 MB, fetched through `NetworkTools` from the two fixed addresses in code and from nowhere else, each at most 32 MiB compressed and 160 MiB expanded, at most 1,500,000 ranges in all, each file refused if it holds no usable range, the old table kept if anything goes wrong. A lookup is a binary search in memory: **no address is ever sent anywhere to be looked up**, and an address on this network (private, loopback, link-local, multicast) is not looked up at all. The holder's name is text somebody else chose, so it is made plain (no control or direction characters, at most 100 characters) and appears only on the traffic view and only as text, never in a finding, an alert, a log, a prompt, a model summary or the Timeline. The table lives in one file registered for factory reset, and the operator can remove it. The country says who an address is registered to, not where a machine stands, and the screen says so.
*   **Only the last summary is kept**, with its time and interface, in one file registered for factory reset: totals, the ten biggest places, the 24 biggest conversations, the internet bytes by holder (at most 8) and by country (at most 12), bytes a second and the status. Nothing in it is acted on.
    *   **Residual risks, accepted:** any peer can send a DNS answer, and any server can be named in a hello, so a name is a hint and a conversation may carry a false one; a hello holds a session ticket and a random value that sit in the privileged helper's memory and the service's for the moment the window is read, and nowhere afterwards; Encrypted Client Hello shows only the front server's name; the table of holders can be out of date or wrong about a range, and a company that serves from many countries shows one; a window shows only this computer's traffic and says so; sampling makes volumes estimates and a frame the kernel drops is missing from them (the screen says how many); a compromised service can ask for a capture and cannot widen what it keeps (the catalogue, the fixed filter and the caps are the limit).
14. **Route Trace** (proposed 2026-11-11, plan `network-traffic-view-redesign`, ADR-0045; amended 2026-11-11 to allow an address the operator types or picks and a repeat of the rounds, plan `network-traffic-more-handoff`, the owner having asked for both; the owner asked for it on 2026-11-11; in force only when the owner merges the pull request that carries this text, which is the owner's approval of the security review). I.2 sends internet traffic through `NetworkTools`, which cannot set a packet's time to live or read the routers' answers; this item allows one more kind of outbound packet, sent by `platform/routeprobe` and by nothing else, on these terms:
    *   **On the operator's press, step-up only.** A trace starts only from the Traffic view's button for one address (`POST /admin/api/netaudit/route-trace`, a step-up route); no schedule, agent, automation, stack or prompt can start one.
    *   **Only an address the operator chose, only on the internet (amended 2026-11-11).** The address is typed into the "Trace a route" card, picked from its fixed presets (1.1.1.1, 8.8.8.8, 9.9.9.9) or opened from a place of the last traffic look (I.13); it is an address, never a name, so no lookup is made. It must be a single internet address (not private, loopback, link-local, carrier-grade NAT, multicast or broadcast), not on the guardrails' blocked list, and the guardrails must allow internet access; otherwise nothing is sent and the screen says why. An address the last look did not see is allowed because the operator's press, behind the passphrase, is the approval; no agent, automation, stack, schedule or prompt can name one.
    *   **Fixed, small probes.** Each probe is one UDP datagram of 24 zero bytes from an unprivileged socket, to destination port 33434 and up (one port per probe), with a time to live of 1 to 30; at most 3 probes at each distance, each waiting at most one second; **optionally (amended 2026-11-11, only when the operator asks for it) 10 more rounds of one probe to each router that answered, one round a second, ending at 60 seconds, so each step shows how many answered and its best, average and worst time**; one trace at a time, with 3 seconds between traces; a trace ends when the address answers, a router says it cannot be reached, five distances in a row are silent, 90 seconds pass, or the service stops. No privilege, raw socket or capability is used: the kernel hands the routers' ICMP answers to the sending socket (`IP_RECVERR`), so this works only on Linux and the screen says so elsewhere.
    *   **What is kept.** Of each answer only the answering router's address, the kind of answer and the time it took. Each router is named from the two tables kept on this computer (I.13 and the city table, ADR-0044); **nothing is sent anywhere to look a router up**, and no reverse lookup is made. The last eight traces are kept in memory only, never written to disk, never a finding, and never in an alert, a log, a prompt, a model summary or the Timeline; the names are shown as text only.
    *   **Residual risks, accepted:** the routers on the way and the address itself see the probes, and learn that this computer traced the route at that moment (they already carry its traffic); a router can answer from any address it likes, so a hop's address and the city given for it are hints; a silent hop is shown as silent, never as missing.

15. **Router Connection Table** (proposed 2026-11-12, plan `network-traffic-more-handoff` B2, ADR-0047; amended 2026-11-12, plan `network-traffic-by-device-redesign`, ADR-0048, to let the audit's own code read it once a night and to keep a history of companies and countries, on the owner's yes of that day; the owner approved the design, the use of `golang.org/x/crypto/ssh` (already in `go.mod`), the stored key and this text on 2026-11-12, after measuring that the RT-AX86U's `/proc/net/nf_conntrack` is readable over SSH (245 lines, no byte counters); in force only when the owner merges the pull request that carries this text, which is the owner's approval of the security review). I.2 sends outbound traffic through `NetworkTools`, which speaks HTTP; this item allows one more outbound connection, an SSH client made by `platform/routerssh` and by nothing else, on these terms:
    *   **On the operator's press, or in the audit's own code while the operator has switched the watch on (amended 2026-11-12).** The setup (address, user, key, the router's key to trust) and the press-read are step-up routes under `/admin/api/netaudit/router-connections`; no schedule, agent, automation, stack or prompt can change the setup. The one other way to a read is the module **Router connections** (a step-up switch, off until the operator turns it on, and only once the setup is finished): while it is on, the nightly report's own code (`netaudit.RouterConnSource`, wired in `internal/app`) reads the table once per audit run, with the same address, user, key and pinned host key, the same fixed command and the same bounds. **No agent can reach the router or what was read from it:** no tool, prompt, task text or setting an agent writes can name the router, the user or the key, ask for a read, change one, switch the module, or read the history. One indirect effect is accepted and bounded: the report's code runs at the end of any automation run that made a scan, so a run in which an agent used the scan tool ends with a read (the agent chose neither whether nor how), and the code reads **at most once every three hours** however many runs there are, a read that fails counting as one; only `internal/app`, the netaudit core and the operator's handlers may import `platform/routerssh`, `routerconn` and `routerhistory`, which the test `TestOnlyTheServiceCodeReachesTheRouter` (IV.6) enforces. A read that fails is said in the report's note and shown as stopped on the Modules tab, never read as "nothing new".
    *   **One private address, one account, one fixed command.** The address is an IP literal on this network (private, not loopback; never a name, never a public or carrier-grade NAT address), with an optional port, saved by the operator. The connection signs in with one key as one account name (letters, digits, dot, dash, underscore, at most 32). The one command ever run is `cat /proc/net/nf_conntrack`: no shell, no pty, no forwarding, no other channel or request, and nothing is written to the router. Output is read to at most 4 MiB, the whole connection ends at 20 seconds, one read runs at a time with 5 seconds between reads, and at most 20,000 lines are parsed.
    *   **The router's key is pinned by the operator.** Before any credential is sent the operator asks the router for its host key (a handshake that is stopped before authentication), compares the SHA256 fingerprint shown with the router's own page, and confirms it; the key is then saved and every later connection refuses a router that shows another, with a fixed message. A new address drops the pinned key. Nothing is ever trusted on first use without that confirmation.
    *   **The key is a secret.** The private key (it must be usable without a passphrase) is stored encrypted in the secrets store (`netaudit/router_ssh_key`), only ever saved, removed or used for a read, never answered back, logged or put in a prompt; a factory reset removes it. The operator is advised to make a key for this alone and to allow SSH on the router for the local network only.
    *   **What is kept.** Of each line only the protocol (tcp, udp, udplite, sctp), the first source and destination addresses and ports (the direction the device made the connection) and a tcp state from a fixed list, as typed values; every other word is dropped. Only a connection from a device on this network to an internet address is kept; connections between devices, to the router itself, to multicast or carrier-grade NAT addresses are not. Connections are grouped per device and place (at most 128 devices and 200 places each), named from the two tables kept on this computer (I.13, ADR-0044) with nothing sent to look an address up, and the last result is kept in memory only: never written to disk, and never in an alert, a log, a prompt, a model summary or the Timeline. **History (amended 2026-11-12):** while the module is on, each read adds to a bounded history on disk (`router-history.json`, at most 128 devices, 64 companies and 32 countries each, the least recently seen going first): per device (by hardware address, else its address on this network) the holder's AS number and name and the country, with the first and last time each was seen; **no address, port, state or connection** is kept. A company or country first seen for a device more than a day after the device's first read, and within the last day, is "new": it is marked on the Traffic tab and raises at most one finding of each kind per device (`router_new_company`, `router_new_country`, low severity, acceptable like any finding), whose evidence is fixed words and the holders' names and country codes from the public tables, never the operator's name for the device. The first day of a device only learns. A factory reset removes the history; switching the module off stops new entries and findings and keeps what was learned. The router keeps no byte counts, so none are shown.
    *   **Residual risks, accepted:** a signed-in operator with the passphrase can point this program at any private address, where the key would be offered (only the router's pinned host key is accepted, so a wrong host is refused after the handshake); a router compromised or reset can show any table, so the list is a hint; connections that ended before the read are missing; the key can sign in to the router for anything the account may do, which is why it should be made for this alone and the router limited to the local network; the table says which device made a connection and to where, which is a record of what each device does and stays on this computer; the history is a longer record of the companies and countries each device used, kept as long as the module is on, so it should be switched off on a computer others can read; a router that is down on an audit night shows as a failed read, and a router whose table lists a company only briefly may be missed or flagged late.

## II. Resource Management (The Bounded Deck)

1.  **Parallel Tool Execution**: To improve efficiency and stay within operational turn limits, the agent loop supports executing multiple independent tool calls in a single turn.
    *   The agent should prioritize batching related filesystem and shell operations into a single turn (The "Rule of Batching") to conserve its execution budget. Each action must still follow the Thought -> Action pattern, but multiple Action blocks are permitted.
2.  **Lifecycle Tethering**: Long-running processes must use a cancellable context derived from the application's root lifecycle. `context.Background()` is permitted only as the application root context (`rootCtx`); a local child context derived from a bare `context.Background()` is insufficient. No untethered background process (Dispatcher, MCP Client, Watcher) may run.
3.  **Sandbox Isolation**: All execution of untrusted code (scripts, binaries, WASM) must occur within the verified `Sandboxing` subsystem. No raw `os/exec` calls are allowed for agent-triggered work. Terminal execution must utilize a persistent shell session to maintain state (CWD, environment) throughout the agent's task lifecycle. **Environment variables passed from the host to the sandbox must be strictly filtered using an explicit Allowlist (defined via `terminal.json` overrides) to prevent secret leakage.**
    *   **Guarded programs** (amended 2026-10-27 after a security review): a guarded program is a known binary that an agent tool starts through `platform/progexec`. (1) Its arguments are built in code from a fixed mode table; the model supplies values for a typed schema, never flags, script names or paths. (2) Its environment is explicit and minimal (`progexec.CleanEnv`: a fixed `PATH`, and `HOME` and `TMPDIR` inside a private per-run directory, plus the program's own data-directory variable); nothing is inherited from the host, and the `terminal.json` allow-list neither applies to it nor can widen it. (3) Every target address is resolved and validated in-process against the operator-declared scan scope before any argument is built; the scope can never contain public, shared (CGNAT), IPv6, loopback, link-local or multicast addresses, and an empty scope means scanning is off. (4) It starts only through the sandbox spawn path, and does not run where the sandbox gives no file confinement (`Effective().Filesystem.Mechanism` is none) unless the operator has opted in. (5) Any script or probe it runs comes from an exact, named, reviewed list; the list may not contain a script that guesses or brute-forces credentials, exploits a flaw, or can open connections to hosts other than the target, and a change to it is a security review. The only credential-bearing exchange the list may hold is a service's well-known anonymous login. (6) Its output is untrusted text: it is parsed into typed fields and reported in fixed wording, never passed on verbatim. **Carve-out from I.1, I.2 and I.3:** the program's own sockets cannot go through `NetworkTools`; the guarantee is instead items (1) to (5), and I.3 holds for the targets as passed to it, not for connections a listed script opens by itself. Anything that sends more than ordinary connections, tries credentials, or could disturb a device is intrusive and is not covered by items (1) to (6) above. **Intrusive runs** (amended 2026-10-30, owner-approved after the real-device test in `network-audit.md` §13.J): an intrusive program run is allowed only when (a) the operator asks for it in the interface for one named device that is inside the scan scope, (b) it never starts from an agent, an automation or any unattended path, (c) its scripts come from a separate exact reviewed list that never contains a script that guesses or brute-forces credentials, exploits a flaw, denies service, or can open connections to hosts other than the target, and (d) each run is rate-limited and time-limited. A change to that list is a security review. Items (1) to (4) and (6) above apply unchanged.
    *   **Unix sockets are refused to every child (proposed 2026-11-06 after a measurement; in force only when the owner merges the pull request that carries this text).** The Landlock filesystem jail does not control the connection to a path-based Unix socket (measured on kernel 6.8, ABI 4: a read outside the grant was denied, a connection to a socket outside it allowed), so a jailed child could reach the system D-Bus or any control socket its user may open. The runner therefore installs a seccomp filter that refuses `socket(AF_UNIX)` and `io_uring_setup` (`platform/sandbox`), for every agent shell, one-shot command and guarded program, unless the spawn site allows Unix sockets for itself in code or the operator writes `sandboxing.unix_sockets: true`. A runner asked for the filter that cannot install it fails before the command runs; on an architecture with no filter (anything but amd64 and arm64) the provider says so (`Effective().unix_sockets`) and does not claim it.
    *   **Local listing programs (proposed 2026-11-06, plan `network-wifi-lookalikes-and-unix-socket-jail`, ADR-0031; in force only when the owner merges the pull request that carries this text).** A guarded program may be one that reads something local and has no target address: `nmcli`, started by `core/netaudit/wifilook` to list the Wi-Fi access points NetworkManager already knows. It is a guarded program in every other respect (items (1), (2), (4) and (6): arguments built in code, a clean environment, the sandbox spawn path, output parsed as untrusted text) and item (3) does not apply because it has no target. It is also narrower than a scanner: its arguments are fixed (`-t -f SSID,BSSID,SIGNAL,SECURITY device wifi list --rescan no`, which asks NetworkManager for what it holds and never to scan), it runs with the Landlock TCP denial (`NoNetwork`) so it cannot open a connection to anything, and it is the one program allowed Unix sockets, which it needs to reach NetworkManager over D-Bus. What it can do there is what polkit allows the service user: measured on the operator's computer (2026-11-06), every state-changing NetworkManager action answered `no` or `auth` for that user (no login session, so `auth` is a refusal), including a rescan. The name of every network it hears is chosen by whoever is in radio range, so it is never kept, shown or sent unless it equals, byte for byte, a network name the operator typed; of every other network nothing is kept, not even a count.
4.  **XML Tool Call Format**: The agent loop must use strict XML tags (`<tool_call>{"tool":"name","args":{...}}</tool_call>`) to delimit actions.
    *   Standard Markdown JSON blocks are prohibited for tool execution to prevent desynchronization with conversational text.
    *   The parser must rely on regex-based XML extraction rather than brace-counting or manual state tracking.
    *   No naked JSON, no markdown fences, no greedy fallbacks.
    *   Rejected formats get specific `ParseError.Feedback()` (defined in `prompts/templates.go`) instead of generic nags.
    *   `sanitizeJSON()` handles Python booleans/None, markdown fences, trailing commentary, and invalid escapes before unmarshaling.
5.  **Dual-Path Tool Interface**: Tool definitions are injected into the system prompt as text (the "Tool Manual").
    *   **Native path**: When `UseNativeTools()` returns true (cloud models, local models with `ToolCallFormat: "native"`), the OpenAI `tools` array is sent in the API request. llama.cpp's Jinja template handles formatting; tool calls are returned server-side.
    *   **Text/XML path**: When `UseNativeTools()` returns false (local models whose serving endpoint cannot produce native tool calls), tools are sent ONLY as text instructions. The model must output `<tool_call>` XML manually, parsed client-side by regex.
    *   **Local capability auto-detection**: A local model with an unset `tool_call_format` is probed once against its serving endpoint (cached on the stored model config) — `"native"` when the endpoint returns native `tool_calls` (llama.cpp `--jinja`, Ollama, LM Studio, vLLM, ...), XML text mode otherwise. This removes the per-model `tool_call_format` patching weak XML-format models used to require.
    *   Explicit `ToolCallFormat: "xml"` always forces XML text mode even if the provider supports native tools; explicit `"native"` forces native tools without probing.
    *   The HTTP client does NOT strip tools — the agent controls this decision.
    *   Both paths coexist: native tool_calls are accumulated from streaming deltas; the XML parser runs as fallback on text content for non-function-calling responses.
6.  **Token Budgeting & Structural Sieve**: To prevent context size overflow and 400-series errors, the system enforces a configurable character-based history budget (default 8,000 characters, overridable per-model via `ModelConfig.ContextBudget`).
    *   **Locked Head**: The System Prompt and the User's Initial Task are immutable and never pruned. In a later turn of a conversation the task is the turn's own question (the newest real user message), which a sieve keeps even though earlier turns sit between it and the head.
    *   **Structural Sieve**: When the budget is exceeded, the history is physically pruned by keeping the Locked Head and the last 10 messages (Priority Tail), while omitting all intermediate turns. This preserves the original goal and the immediate state while ensuring the context window is never overwhelmed.
    *   **Progress Ledger**: Every sieve (physical, reactive, aggressive) inserts, right after the byte-exact `SieveSystemNote`, one deterministic ledger message built in code (`assistant/ledger.go`) from the run's finished tool calls (✓/✗, tool, key argument, and for terminal commands/failures a short result head). It states facts only (`prompts.SieveLedgerHeader`), never calls an LLM, is bounded to a share of `ContextBudget`, replaces — never stacks beside — an earlier ledger, and is registered in `IsAgentControlMessage`. In-place compression is idempotent so messages that were already truncated keep their bytes between prunes. A new prune REPLACES the previous sieve note, ledger and warning (never stacks them), and the physical sieve's "deliver your final answer NOW" warning is sent ONCE per run (`sieveState.contextWarned`): on a small window the sieve fires on later turns too, and a run that keeps working is not told to stop every turn — later prunes still refresh the note and the ledger.
    *   **Reactive Sieve**: When the LLM returns a context-size overflow error (e.g. `request exceeds the available context size`), the agent applies an aggressive sieve (system + task + last 3 turns) and retries.  This catches cases where the character-budget sieve didn't fire because the model's actual token context is smaller than expected (e.g. llama.cpp with `--ctx-size 8192` but metadata reporting 262K training context).
    *   **Repetition Detection**: The repetition detector (`recentCalls`, `duplicateStreak`) survives sieve boundaries to prevent loops from spanning across prune events. After 3 consecutive identical (tool + args) calls, inject a duplicate nag. After 5+, abort with "infinite loop detected."
    *   **Resource-Aware Orchestration**: A higher-level token and cost budgeting system (see Section VI) may further constrain model usage. The Structural Sieve reduces context pressure; the Orchestrator enforces hard ICU caps and applies adaptive squeezing when approaching those caps. Both systems coexist — the Sieve prunes history, the Orchestrator limits per-request and per-window token consumption.
7.  **Natural Task Completion**: The agent completes a task when it produces a final assistant message with substantive visible content (≥20 characters after stripping inline reasoning blocks such as `<think>`/`<reasoning>`) and no further tool calls. Completion requires at least one tool result anywhere in the run's history — the model must have actually done work, not just answered from first-turn text. Reasoning-only interleaves between tool results and the final answer do not block completion; the immediately-preceding message is not required to be a tool result. The synthetic `submit_final_answer` tool is removed (commit `f89b2cf`, PR #27). Heuristic keyword matching ("task complete", "summary") is not used. When the model returns empty after tools, the agent issues a single nag ("continue with the task") rather than looping indefinitely; if the response is still empty, a fallback answer (saved content-with-tools or best-available assistant text) is used. Exception to completion: a content-only turn whose stream ended with `finish_reason="length"` (output-token cap) is a truncated answer, not a completion — the loop keeps the partial and nudges a bounded continuation ("continue exactly where you left off") until the cap stops firing or `lengthContinuationMax` is reached, stitching the fragments into the final report (mirrors Hermes's length-continuation; see SPEC-001 §5).
8.  **Context-Preserving Normalization**: Messages transmitted to LLM engines must be stripped of non-essential metadata fields. `role`, `content`, `tool_calls`, and `tool_call_id` are preserved.
    *   When native tools are disabled: `tool` role → `user` role with tool_call_id embedded in content (`Tool result [call_N]: <json>`) to maintain call/result association while avoiding Jinja template errors in llama.cpp backends.
    *   When native tools are enabled: tool roles pass through as-is.
    *   **No Auto-Nags in Normalization**: Nag injection (prompt corrections when the model produces malformed tool calls, duplicate detection, feedback injection) belongs in the agent loop (`agent.go`), NOT in `NormalizeHistory()`. The history normalizer must not modify message content beyond role conversion and metadata stripping.
9.  **Structural Truncation**: High-volume tool outputs must be structurally truncated (Head/Mid/Tail) before being returned to the context window.
10. **Guardrail Decision Flow**: When a tool call is blocked by the guardrail engine, the agent loop must pause and wait for user approval rather than silently failing.
    *   `ValidateToolCall()` fails → creates `GuardrailBlockedPayload` with decision_id.
    *   `onGuardrail` callback registers a channel in `GuardrailDecisionStore` + publishes SSE event to frontend.
    *   Agent blocks on channel (bounded by the per-model `guardrail_approval_timeout_seconds`, default 5 min).
    *   User approves/denies via `POST /admin/api/conversation/guardrail-decision`.
    *   If approved with `persist: true` → `PersistOverride()` writes to workspace `config.yaml`.
    *   In automation mode (no user present), the callback is nil and guardrail violations fail immediately.
11. **Per-Model Config Flow**: `ModelConfig.MaxSteps`, `ContextBudget`, `MaxTokens`, `ToolCallFormat`, and `Prefill` flow from the runtime to the agent without global defaults interfering.
     *   Read by the executor from `Runtime.ListModels()`.
     *   Passed to `AgentOptions` when creating the Agent.
     *   The agent uses them directly — no global defaults override per-model settings.
     *   Provider-tier defaults (`assistant/agent.go`) define baseline values for each provider type (local, gemini, openai, openrouter, etc.). These defaults are applied when creating new model entries but do not override explicitly set per-model values.
12. **Agent Memory System**: The agent can persist and recall facts across conversations via a SQLite-backed memory store.
      *   **Storage**: Memories are stored in a dedicated `memories` table with an FTS5 full-text index (`memories_fts`) in `orchestrator.db`, sharing the same database file as the ledger. The `memory.Store` package (`internal/platform/memory/`) provides all CRUD and search operations.
      *   **Tools**: `memory_search`, `memory_update` and `memory_forget` are registered tools. `memory_search(query, scope, tags)` performs FTS5 keyword search with BM25 ranking and optional scope/tag filtering; `memory_update(content, scope, mode, keep, old_text, separate)` saves a memory with three-tier routing, and a fact similar to a stored one is reported to the model (to replace with `old_text` or keep with `separate`) instead of being concatenated; `memory_forget(text)` deletes a saved fact. **Security review of `memory_forget` (2026-10-16):** it deletes only when exactly one saved fact matches, only in the operator's own chat (never in an automation or a connector chat, so an outside sender cannot erase what the owner saved), and returns the deleted text; it is a mutating tool, not housekeeping. **No save path stores a secret:** `memory_update` and `SaveFact` refuse secret-shaped strings and statements of a credential's value in code (`tools.ErrSecretContent`), whatever the prompt says.
      *   **Active Memory Injection**: Once per run (`Execute`), before the first request, the agent snapshots every hot (`mode: "always"`) entry via `SearchHot` using the run's context — no FTS5 query. The snapshot is rendered once as a `<memory>` block and appended to the **head system message** of every request in that run, so the prompt prefix is byte-identical turn to turn (llama.cpp reuses its KV cache only for an identical prefix; a block that moves or changes per turn defeats it, and a mid-conversation system message breaks some chat templates). Facts saved mid-run become visible on the next run. **Operator notes (MEMORY.md):** the operator's own standing notes — a global file in the config root and a per-workspace file in that workspace's metadata folder, both OUTSIDE the agent's workspace jail so an agent cannot rewrite text that rides in every prompt — are read in the same once-per-run snapshot and placed first in the block (`prompts.HotMemoryOperatorHeader`), ahead of the saved facts, which they outrank. They are bounded to 6000 chars per file on write (atomically), and at injection they **share the cap with the saved facts**: the block never exceeds the model's memory cap, the notes outrank the facts, the facts reserve the room they need up to a quarter of the block, and notes that do not fit are cut at a line boundary (each file keeping a fair share) with a visible hint naming how many characters are missing; the preview reports it as `notes_cut_chars`. (Amended 2026-10-16: notes were never clipped and could be several times the cap, pushing every saved fact out of a small window.) The block is capped to a share of the model's resolved `ContextBudget` (local 8%, cloud 5%, clamped to 400–6000 chars; 2000 when the budget is unresolved), ordered by operator priority (high, normal, low; `memories.priority`, default normal, set only by the operator) then newest first, cut on entry boundaries from the tail, so high-priority facts are cut last; when entries are cut the block ends with a hint naming `memory_search` and the number left out. The sieve's budget measurement includes the block. Automation runs get no memory injection by default (the full task prompt is too generic as a search query). An automation may opt in with `memory_mode: hot` (typed `models.MemoryMode`, default off/unset, validated at the HTTP boundary): the run then receives the same frozen head-system block as a chat — the original objection (a block at the end of 18+ turns of history overwrote the finalization instruction) no longer applies because the block is static in the head, never near the tail. Unattended runs (`models.WithUnattendedRun`, stamped by the automation executor) write with conservative defaults: an unspecified `memory_update` is `keep: session` and every entry is sourced `run:<run id>`; an explicit `keep: permanent` is honoured. A lifecycle-owned `memory.SessionReaper` (started in `app.New`, tethered to the root context) deletes only `session` entries older than `memory.retention_days` (default 90; non-positive/absent falls back to the default, never "forever"). See `docs/audits/memory-injection-investigation.md` for the rationale. All prompt strings live in `templates.go` (Constitution II.12 applies).
     *   **Usage counters**: each fact carries `injected_count` (runs it was actually sent in — facts the budget cut are not counted, once per run), `searched_count` (times `memory_search` returned it) and `last_used_at`. Recording is an in-memory increment (`Store.RecordInjected/RecordSearched`); a lifecycle-owned `memory.UsageFlusher` (started in `startMemoryJobs`, tethered to the root context) writes the deltas in one transaction every 30 s, once more on shutdown, and `App.Shutdown` flushes synchronously — no database write ever sits on a run's path. A failed flush keeps the counts; a crash loses at most one interval. Operator browsing and the preview never count.
     *   **Pre-Sieve Flush**: When context usage exceeds the flush threshold (default 70% of `ContextBudget`), a nudge message is appended asking the agent to save important context to memory via `memory_update`. A `memoryFlushSent` flag prevents repeated nudges across consecutive turns; the flag resets when the physical sieve actually prunes history.
     *   **Configuration**: Memory is configurable via `UserSettings.Memory` (Tier 2 settings.yml). `Enabled`, `SearchTopK`, `FlushThreshold`, and `RetentionDays` are user-settable. When disabled, the memory store is nil and all operations are no-ops.
     *   **Workspace Isolation**: All queries filter by `workspace_id`. Agents in different workspaces have independent memories.
     *   **Lifecycle Events**: `memory_recall` and `memory_flush` events are emitted to the UI for observability.

13. **Prompt Centralization** (SINGLE SOURCE OF TRUTH): `internal/core/assistant/prompts/templates.go` is the ONLY location for ALL prompt strings.
14. **Goroutine Lifecycle Discipline**: Every goroutine must have an explicit termination path via `context.Context` or channel close. `context.Background()` is permitted only as the application root context (`rootCtx`); a local child context derived from a bare `context.Background()` is insufficient. Orphan goroutines — those without cancellation, timeout, or completion signaling — are prohibited. This applies to background workers, heartbeat loops, stream processors, and timer-based routines.
    *   System messages, nag prompts, parse-error feedback, JSON error translations.
    *   Escalation prefixes, protocol instructions, system rule text.
    *   No hardcoded prompt strings anywhere else — not in `agent.go`, not in `tool_call_parser.go`, not in any other logic file.
     *   When adding or modifying a prompt, `templates.go` is the only valid location.

## III. Data & Metadata (The High-Fidelity Rule)

1.  **GGUF Parsing**: Parsing of GGUF metadata must use the authorized parsing library (`internal/core/llm/metadata/gguf_scanner.go`). String manipulation or regex-based extraction from filenames is forbidden. The scanner reads only the GGUF header (KB, not GB) using `SkipLargeMetadata` + `MMap`.
2.  **Atomic Persistence**: All system configuration writes must be atomic. Use `storage.Update` patterns to prevent partial state corruption.
3.  **Workspace Jail**: File system access for agents must be strictly jailed to the assigned workspace directory using `IsSecurePath`. The system root is never a valid target for agentic I/O. Terminal commands must be validated using segment-aware parsing to ensure chained commands (e.g., `&&`, `||`, `;`, `|`) do not bypass security guardrails.
4.  **Three-Tier Configuration Model** (XDG relocation — see `docs/PLANS/ARCHIVE/cross-cutting/xdg-config-data-relocation.md`):
    *   **Tier 1+2 — `settings.yml`** (operator + user, single owner): `AppConfig` absorbs the legacy `config.json` (server, workspaces_dir, metrics), `host.json` (sandboxing), and `settings.yml` (local paths, guardrails, model overrides, memory, run_logging). `DataManager.System()`/`.Settings()` are facade views over the one store; every write persists the complete merged document under one mutex.
    *   **Tier 3 — `registry.json`** (dynamic state, CONFIG root): Model catalogue, provider definitions, MCP server list, communication connector configs, primary/fallback models.
    *   **Canonical locations** — Single root (`~/.config/llm-proxy` or `LLM_PROXY_HOME`): all files — `settings.yml`, `registry.json`, `secrets.json`, `master.key` (+`.hash`), `orchestrator.db` (+wal/shm), and the `templates/`, `meta/`, `runs/`, `logs/` subdirectories — live under one directory tree. `Paths.ConfigDir` and `Paths.DataDir` both resolve to this single root. The `master.key` and encrypted `secrets.json` are co-located for operator convenience; 0700 directory mode and 0600 file modes provide security at rest.
    *   **Workspace overrides** — `{root}/meta/{workspace}/config.yaml`: Per-workspace guardrails, automations, and settings. Runtime state never lives under the workspace tree.
5.  **Model Persistence (Two-Tier)**: Model configuration is split across two persistence locations:
    *   **Base model info** → `registry.json`: name, provider, filename/model_id, port, args, credential_id, prefill flag.
    *   **Agent tuning overrides** → `settings.yml` under `model_overrides:`: max_steps, context_budget, tool_call_format, prefill.
    *   On save: both tiers are updated simultaneously.
    *   On load: registry.json base is loaded first, then `ApplyModelOverrides()` merges settings.yml overrides onto runtime models.
    *   On settings change: `ApplyModelOverrides()` re-applies overrides to all runtime models.
    *   **Never put agent tuning overrides directly in registry.json entries.**
6.  **Secrets Are Encrypted**: API keys and tool secrets are stored in `secrets.json` (under the CONFIG root, e.g. `~/.config/llm-proxy/secrets.json`) encrypted with AES-256-GCM. The AES-256 master key (`master.key`) lives in the same CONFIG root, so all credential artifacts are co-located in one directory for operator convenience. The `SecretsStore` interface is the only access path. Both roots are 0700; `master.key`/`.hash`/`secrets.json` are 0600.
7.  **Key Deletion/Update Cascades to Models**: Deleting or updating API keys automatically removes all model catalogue entries whose `CredentialID` no longer matches any remaining key name. Models with an empty `CredentialID` are only removed if no keys remain for the provider. This prevents orphaned model configurations that reference deleted or renamed credentials. Cascade applies on both `DELETE /admin/api/secrets/keys` (single-key) and `PUT /admin/api/secrets/keys` (batch save).
8.  **Unified Provider Management**: All cloud provider configuration (API keys, provider settings, and model entries) is managed under a single provider tab in Settings. The Dashboard cloud tab is read-only — model management ("Add Model", edit, delete) is done exclusively in Settings. This eliminates the previous split where API keys were managed in Settings and models were managed in the Dashboard.
9.  **Secrets Change Notification**: The secrets store publishes an `OnChange` event when credentials are modified. The `AppContext` subscribes to this event and triggers a runtime `Sync()` to ensure credential changes propagate without requiring a server restart.

## IV. Code Standards (The Clean Signal)

1.  **Context Propagation**: Every function performing I/O or network calls MUST accept `context.Context` as its first argument.
2.  **Error Integrity**: Never return raw strings as errors. Always use `fmt.Errorf` with the `%w` verb to maintain the error chain for diagnostic trace-back.
3.  **Failover Clarity**: Distinguish between "Transitional States" (e.g., loading weights) and "Terminal Errors". Fallback logic should only trigger on terminal failures.
4.  **No Dead Code**: Remove unused imports, variables, and functions. Do not leave `_` prefixed variables as placeholders.
5.  **Testing Standards**: Mock the interface, not the implementation. All `RuntimeManager` mocks implement the full interface (`MockManager`). Test the agent loop with real tool providers where possible; mock only the LLM client.
6.  **Stack Boundaries** (proposed 2026-11-06, plan `stacks-as-packages-and-network-stack`, ADR-0032 and ADR-0033; in force only when the owner merges the pull request that carries this text, which is the owner's approval of the security review). A stack is its own Go module under the repository's `stacks/<name>/` folder, outside `backend/`, with a manifest; the contract it uses is the module `stacks/sdk`. The rules below are enforced by tests, not by review alone, and they keep a stack movable to its own repository or process later without a redesign. They do not themselves create a process boundary: every stack runs in the one service under the one unit.
    *   **Imports.** A stack imports the standard library, third-party libraries and `llm-proxy-stacks/sdk`; never `llm-proxy/internal/...`, `llm-proxy/models` or another stack. Its `go.mod` requires nothing of ours but the SDK. Nothing under `backend/internal/` imports a stack except the one wiring file (`internal/app/stacks.go`). The compiler enforces most of this (a separate module cannot see `internal/`), and a test over `go list` and each stack's `go.mod` fails the build on any breach the compiler allows (a `go.work` workspace lets a stack see the service's exported packages, so CI also builds each stack with the workspace off).
    *   **The SDK is contracts only:** interfaces, plain data types, the manifest and validation. No feature logic. The network guard (I.1 to I.3) and the sandbox (II.3) are reached only through it; a stack cannot dial or start a program any other way.
    *   **Plain data across the boundary.** Every call, result, event and configuration value between a stack and the core is a struct of serializable fields: no functions, channels, pointers to shared state, or live handles. A test round-trips every port call through JSON.
    *   **A stack owns its storage;** the core reads it only through the stack's interface. **Events** are typed messages published through the SDK, not a direct use of the event bus. **Configuration** arrives as a value the stack re-reads on change; it never reaches into the global settings.
    *   **Errors cross as a code and a message** (an SDK error type), never as a Go error compared by identity. Inside the stack, IV.2 still applies.
    *   **Tools are declared as data** in the manifest (name, schema, category); the handler is invoked by name with JSON arguments and returns JSON.
    *   **Stacks never call each other directly;** a call between stacks goes through an SDK port.
    *   **No new way around a guard.** A stack cannot declare a privilege, switch off or relax the sandbox, widen the scan scope, or change the unit's hardening. Anything that needs one is a Constitution amendment of its own. A request to the privileged helper (I.11) is a request the core mediates through an SDK port, not a declaration: a manifest still cannot add an action to the catalogue.
    *   **Scope.** Code under `internal/` that is not yet in a stack is outside this item until a plan moves it.

## V. Governance (The Living Law)

1.  **Constitution over Convenience**: If a feature requires violating these laws, the law must be formally amended in the Constitution after a security review, rather than bypassed in the implementation.
2.  **Spec-First Development**: Before modifying a subsystem, read its corresponding SPEC (`docs/SPECS/`, cataloged in `docs/INDEX.md`). After implementing, update the relevant spec and amend this Constitution if architectural rules changed.
3.  **No Half-Finished Implementations**: Complete the feature or don't start. Do not introduce stubs, `// TODO`, or feature flags for incomplete *new* work. Preserve unrelated existing TODOs unless the task explicitly addresses them.
